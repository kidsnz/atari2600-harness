# Technique — 6502 / kernel micro-idioms (instruction-level tricks: Combat §1-5, mailing list and forums §6-33)

**Source:** studied clean-room from the annotated *Combat* disassembly (Roger Williams' `Combat.asm`), deep-read harvest 2026-07-23 〔Combat.asm kernel + movement + score routines〕. **Reference idioms** (label names + generalized prose only) — *not yet reimplemented / CI-locked*; standalone demo + scenario = TODO. Each is an instruction-level packing / aliasing / branchless trick that saves cycles or bytes in the tightest loops.

## 1. Smuggle a second axis in the LOW nibble of an HMP byte
TIA's `HMPx` latch samples only bits 4-7 (the **high** nibble), so the low nibble is inert to hardware — free storage for a second datum in the same byte.
- A heading table (`Xoffsets` / `HDGTBL`) is **one byte per direction that drives BOTH motion axes**: `STA HMP0,X` sets horizontal HMOVE motion (high nibble), then the *same* byte is reused `AND #$0F / SEC / SBC #$08` to turn the low nibble into a **signed vertical step (−8..+7)** added to the object's Y. One table, one byte, both axes 〔PhMove, Xoffsets, HDGTBL〕.
- **PF0 is a second carrier.** It also shows only its high nibble. Thomas Jentzsch drives two playfield registers from one RAM byte on the right half of a non-reflected PF — `lda PF02Data,x / sta PF0` (bits 4-7) `/ and #$0f` (+2 cycles) `/ sta PF2` (bits 0-3) — answering the worry that a non-reflected PF would add *"another 32 bytes to the RAM usage"* 〔stella-list `200405/msg00068`〕. Glenn Saunders had proposed the same split in 2003 for a left and a right wall: one byte per row, PF0 with no mask *"because the register only uses the left 4 bits"*, *"for PF2 you will need to mask the left half first"*, one zero-page index stepping both sides, and PF0 and PF2 still blanked so they do not repeat — *"Thinking on my feet"*, a suggestion rather than a kernel 〔`200309/msg00065`〕. piledriver put a run-length count in the same spare nibble, taking a 4K game from about 4 screens to 16 〔AtariAge `topic/367878`〕. **Cited only, not verified.** (Not the two-lines-per-byte PF0 packing further down: there the low nibble is the next line's PF0.)
- **Four registers from one byte.** mikes360's rail macro: `lda (railGfxPtr1),y / and (railMaskPtr),y / sta ENAM0 / sta HMM1 / rol / sta ENAM1 / rol / and #%00110000 / sta NUSIZ1`. It holds because *"HM's don't care about the low nybble. Likewise, ENA's don't care about anything except bit1"* (Nukey Shay), so one byte carries HMM1 in bits 4-7, ENAM0 in bit 1, ENAM1 in bit 0 (bit 1 after one `rol`) and the NUSIZ1 missile size in bits 2-3 (bits 4-5 after two) 〔AtariAge `topic/233300`〕. **Cited only, not verified** — the bit positions are traced by hand from the posted code. Christopher Tumber had packed a missile the same way in 2003: `lda Missile_Data_Table,x / sta HMM0 / sta ENAM0 / asl / asl / sta NUSIZ0`, the table's bits 7-4 HMM0, bits 3-2 the missile width (bits 5-4 after the two `asl`), bit 1 ENAM0, bit 0 unused — 24 cycles with the `tya / sbc Vertical_Position / tax` in front, by his own account slower than the routine he was answering, but able to blank the missile in the middle of its height 〔stella-list `200301/msg00306`〕. That `sta NUSIZ0` also writes player 0's bits 0-2: bits 0-1 are 0 after the shifts, and bit 2 is the table's unused bit 0, so they are 0 only if every table byte keeps that bit clear (our reading). **Cited only, not verified.**
- **A position in one byte.** Eckhard Stolberg: *"store the horizontal position of your objects in the high and low nibble of a byte for each. The high nibble would hold the value for the HMOVE and the low nibble would hold the value for the @1:DEY/BPL @1 delay loop"* — `STA WSYNC / LDA ypos0 / STA HMP0 / AND #$0F / TAY / @1:DEY / BPL @1 / STA RESP0 / STA WSYNC / STA HMOVE` (his name for a horizontal position), the whole byte going to HMP0, which reads only the high nibble. Moving is *"adding or subtracting #$10 from the ypos value and checking if the high nibble has rolled so that the low nibble has to be fixed accordingly"*; a second player at a fixed distance can be placed on the same line, otherwise it needs a second delay loop before the HMOVE 〔stella-list `199803/msg00156`〕. One byte of RAM per object (our reading). **Cited only, not verified.**
- **One immediate as the threshold and the value.** Thomas Jentzsch's *Thrust* kernel: `lda #MAXDIR/2-1 ; bit 3 is enabled here / cmp P1dir / bcs .noReflect / sta REFP1 ; enable bit 3`. With `MAXDIR = 32` the immediate is 15 (`$0F`), the last direction drawn unreflected, and REFPx reads only D3 (`sprite-animation.md`), so the constant the compare needs is also a value that reflects 〔stella-list `200203/msg00009`〕. The store only sets the reflection; where it is cleared for directions up to 15 is not in the post. **Cited only, not verified.**
- **A colour's low bits as an adder's seed.** Christopher Tumber's line set C with `sbc` / `cmp`, wrote `lda #wallcolour / sta COLUPF`, then `lda #1 / adc #0 / sta ENAM0` — 1 or 2, and ENAMx reads only D1 〔stella-list `200307/msg00023`〕. Thomas Jentzsch: *"If you make sure that bit 0 of #wallcolour is always set you can avoid lda #1"* 〔`200307/msg00028`〕 — A still holds the colour when `adc #0` runs. Tumber counted 4 cycles, both `lda #1`s 〔`200307/msg00029`〕, then corrected the condition: *"I have to be sure the lower two bits are always 01. If they're 11 I'm in trouble"* 〔`200307/msg00031`〕; Jentzsch: *"You can also use e.g. adc #1 instead and make sure the lower two bits are 00"* 〔`200307/msg00040`〕. Nothing is masked here, because the consumer ignores the bits. D1 is the colour's lowest luminance bit (`pkg/design/color.go`), so either form leaves that colour four of the eight luminances (our arithmetic). **Cited only, not verified.**
- **Idiom.** Any TIA register that ignores some bits is spare storage — pack another field there and mask it out (`AND`) when you consume it.
- ★**Trap: stepping a packed byte with `INX`/`DEX`.** Darrell Spice kept a colour in the high nibble of X with the low nibble zero, and one joystick direction stopped registering 〔stella-list `200404/msg00356`〕: *"DEX decreased the high-nybble by one, but INX increased the low-nybble by one w/out affecting the high-nybble"* 〔`200404/msg00361`〕. From `$A0`, `DEX` gives `$9F` (high nibble `$A`→`$9`) and `INX` gives `$A1` (high nibble still `$A`). His fix: `LSR` four times before the value goes into X, `ASL` four times after it comes back out. The arithmetic is checked; his program is **Cited only, not verified**.

## 2. Store a boolean as `$FF`/`$00` and spend it directly as an AND-mask (branchless blank)
Choose a flag's **representation** so it can be `AND`ed with data to pass-or-zero with no branch: `$FF`/`$00` (byte) or `$0F`/`$00` (nibble).
- `LDA glyph,Y / AND SHOWSCR` blanks the right-hand score when `SHOWSCR=$00`, passes it when `$0F` — no branch in the score kernel.
- The **same** flag pattern masks across subsystems: `AND GameOn` (`$FF` playing / `$00` attract) zeroes engine volume to mute during attract, and gates a timer's increment. One boolean, reused as a universal branchless gate over score, sound, and input 〔VSCOR AND SHOWSCR; DOMOTOR / NoNewGM AND GameOn〕.
- **The loop index as the flag.** ENAMx reads only D1, so if a kernel's index runs through Y = 2,3,6,7,10,11… (graphics spread out in ROM to match), writing Y to ENAMx lights the missile with no test at all; Y = 0,1,4,5,8,9… turns it off the same way (Omegamatrix, for a score kernel) 〔AtariAge `topic/221811`〕. **Cited only, not verified.**
- **Where to keep a flag you test in a hurry: bit 7 or bit 6.** SpiceWare: *"use the top 2 bits for anything time critical as they can quickly be tested for"* — `BIT zp` then `BPL`/`BMI` (bit 7) or `BVC`/`BVS` (bit 6), which leaves A, X and Y untouched; any other bit takes `LDA zp / AND #mask` and a branch, *"the A register, and 2 extra cycles"* 〔AtariAge `topic/344945`〕. From `definitions.json`: `BIT zp` 2 bytes / 3 cycles (`$24`), `LDA zp` + `AND #` 4 bytes / 5 cycles (`$A5`, `$29`). `docs/resources.md` reads TIMINT and PA7 the same way (*BIT TIMINT / BMI expired / BVS pa7*); this is the same instruction turned into a rule for laying out your own RAM. **Cited only, not verified.**
- **A test's polarity as an immediate.** pantomchap read the fire button with `lda #%01111111 / eor INPT4 / bmi`; changing the immediate to `#%10000000` turns D7 over, so the same code branches on the opposite state. The broken picture he blamed on that change Andrew Davie put, *"probably"*, down to `$80`, which that branch's target `fireisnotchecked` increments with no upper bound 〔AtariAge `topic/265967`〕. Against `bit INPT4` (`BIT zp` above) it costs A, 2 more bytes and 2 more cycles (`$A9`, `$45`); what it buys is that the state that branches is a constant, which could come from a table (our reading — the thread does not say so). **Cited only, not verified.**
- **Idiom.** Match a boolean's bit pattern to how it's consumed; an all-ones / all-zeros flag is a free conditional-blank (0 cycles of control flow).

## 3. Pre-bias a table pointer by the loop's fixed offset to delete a per-scanline add
If a kernel indexes a table with a counter that is always a **constant** higher than the data row, bake that constant into the stored pointer instead of adding it every line.
- The playfield column pointers (`PLFPNT`) each point **4 bytes before** the real data (`PF0_0-4`, `PF1_0-4`, `PF2_0-4`). The kernel's `LDA (LORES),Y` uses a Y that is naturally `+4` (the top 4 skipped lines); the two cancel, so the tightest loop never pays a `+4` add. (Author's note: "these addresses point 4 bytes before the real start of data.") 〔PLFPNT, LORES, InitPF〕
- **A bias that moves with the sprite.** Thomas Jentzsch, for a car fetched with `LDA (P0_CurrentFramePtr),Y` where Y is the kernel's one row counter: point the pointer at the graphics *minus* the row where the car starts — `LDA #<CarRotation0 / SEC / SBC #50 / STA ptr / LDA #>CarRotation0 / SBC #0 / STA ptr+1`, the borrow carried into the high byte — so the fetch indexes with the row counter itself 〔stella-list `200110/msg00087`〕. Manuel Polik: this runs outside the kernel, and *"If we fall below zero here, we cross a page later"*, so the data must sit high enough in its page (Jentzsch, for a 180-line two-line kernel: between `256*n+180/2` and `256*(n+1)-1`) 〔`200110/msg00093`〕. The bias is a per-frame variable here, not a constant. **Cited only, not verified.**
- **Idiom.** Fold a constant index bias into the **pointer constant**, not into the loop body.

## 4. Vertical playfield mirror by EOR-ing the scanline counter
Draw one PF map symmetrically top **and** bottom by reflecting the *index*, not duplicating data. The scanline counter's sign bit picks the half; for the bottom half `EOR #$F8` mirrors the fetch index so the same column data is read symmetrically:
```
LDA ScanLine
BPL VvRefl        ; top half: use index as-is
EOR #$F8          ; bottom half: reflect the index
VvRefl: … LDA (LORES),Y
```
〔Vfield BPL VvRefl / EOR #$F8〕
- **Idiom.** Vertical symmetry costs **one EOR on the loop counter**, not a second table. (Distinct from sprite 180° mirror via `REFP` + reverse-copy — this is the playfield index-reflect mechanism.)
- **The opposite trade: repeat the data so the index never wraps.** Thomas Jentzsch took a scrolling playfield's per-line bookkeeping down from 22 cycles (Jake Patterson's table-driven version) in steps 〔stella-list `200111/msg00186`〕: a plain down-counting rewrite was *slower*, 27 worst case; keeping the block index in X instead of RAM made it 18; *"repeat the data X (was BufferPointer) is pointing at. That will cost you some ROM, but now you never have to check and reset X"* made it 14; and Y as the line counter with blocks *"2^4 (=16) lines high"* — `TYA / EOR Offset / AND #15 / BNE / INX` — made it 11, the `Offset` value left as *"You have to test this"*. Patterson declined the repeated data because ROM held his level list; Jentzsch: *"then simply don't use this optimization. The rest will work without it"* 〔`200111/msg00191`, `200111/msg00202`〕. The reflection above saves a copy and pays an `EOR`; this pays for a copy to delete a test. **Cited only, not verified.**

## 5. Compare-via-EOR at a loop exit to harvest A=0 for the teardown clear
When a loop terminates on a specific counter value, exit with `EOR #value` instead of `CMP #value`: at the terminating value the EOR yields `0` and falls through with **A already zero**, which the next block spends directly to clear registers — saving the `LDA #0` before the tear-down.
```
EOR #$EC
BNE Vfield        ; not the last line → keep looping
; falls through with A = 0:
STA ENAM0 / STA ENAM1 / STA GRP0 / STA GRP1 / STA PF0 / STA PF1 / STA PF2
```
〔VnoPF EOR #$EC → STA ENAM0..PF2 clear block〕
- **Idiom.** If a loop's exit value is a constant **and** the next thing you do is zero registers, `EOR`-compare hands you the `0` for free — `CMP` would leave A holding the old counter value.
- **When the register reads one bit, `LSR` can stand in for `LDA #0`.** VSYNC uses only D1. In the VSYNC routines of Thomas Jentzsch's *Turbo*, as Manuel Polik disassembled them, `LDA #$02` turns it on and a later `LSR` leaves A = `$01`, which turns it off — 1 byte where `LDA #0` is 2, both 2 cycles (`$4A`, `$A9`) 〔stella-list `200304/msg00025`〕. **Cited only, not verified.**
- **A clear loop hands over its zero too.** Chris Larkin, reading Adam Wozniak's first program: one `ldx #$00` already served `AUDV0`/`AUDV1`, so the next `ldx #$00` a few lines later was not needed, and *"after your memory clear loop is finished, the accumulator has been decremented to #00, so you can even just load these values there"* — put the zero stores straight after the loop 〔stella-list `200301/msg00006`〕. The loop itself is not in the post. **Cited only, not verified.**

## 6. Equal-cost branch arms: swallow the taken arm's instruction with one opcode byte
SpiceWare's paddle read from *Medieval Mayhem* costs the same whether or not the pot has tripped 〔AtariAge `topic/246976`〕:
```
lda INPT0          ; 3
bpl .save          ; 2 not taken / 3 taken
.byte $2D          ; 4 / -   AND abs: eats the next two bytes
.save sty Paddle1  ; - / 3
```
Not taken 2 + 4, taken 3 + 3: 9 cycles either way. The counts are from the engine's opcode table (`Gopher2600/hardware/cpu/instructions/definitions.json`: `$2D` 3 bytes / 4 cycles, `$84` 3 cycles, `$10` 2 cycles; a taken branch adds 1, and 1 more across a page). **Not verified** — the macro was not assembled or run.
- ★`$2D` is **`AND abs`, not `BIT abs` (`$2C`)**: it changes A and N/Z, which is harmless only as long as the code after the macro does not use them (the thread does not show that code). The address it reads is `$PP84` (`$84` = the `sty zp` opcode, PP = Paddle1's zero-page address). A7 of `$84` is 1, so TIA is never selected (the hazard in `docs/fundamentals-audit.md`, *BIT-as-NOP reads*); A12 is bit 4 of PP, so for PP = `$80`-`$8F`, `$A0`-`$AF`, `$C0`-`$CF` or `$E0`-`$EF` A12 is 0 and the read goes to RIOT — its RAM, or its I/O and timer when PP's bit 1 (A9) is set (e.g. `$284` INTIM). With A12 = 1 it reads cartridge space, where RAM ports and hotspots still have to be checked against the scheme. **Not verified** — derived, not measured.
- The harness has the principle (`docs/integration-density-playbook.md`, *"balance branch arms so every path costs the same"*) and the byte-skip for another purpose (`roms/techniques/tia_pcm.asm`, `BIT abs = skip the next 2-byte LDA #0`); this is the one-byte way to make two arms equal.
- **Branch to the skip, not to the draw.** walaber's sprite routine branched to the drawing arm — `TXA / SEC / SBC PlayerPosY+1 / ADC #C_PLAYER_SPRITE_HEIGHT / BCS .DrawPlayerTaxi`, the other arm three `NOP`s and `SEC / BCS .DoneDrawPlayerTaxi` — *"it takes 22 cycles"* either way. Thomas Jentzsch: *"Instead of branching to .DrawPlayerTaxi draw to something like .SkipDrawPlayerTaxi and from there back to .DoneDrawPlayerTaxi. That saves one cycle. Maybe you can make sure that the carry is always set. That would save another 2 cycles"* 〔AtariAge `topic/249398`〕. The drawing line then falls through an untaken branch, 2 cycles instead of 3; which `SEC` the carry remark removes is not said. The skip-draw itself is in `vertical-positioning.md`. **Cited only, not verified.**
- **The same move when every path must cost the same.** Fabrizio Zavagli's *Bounce!* kernel has no `WSYNC`, so a routine had to take exactly 150 cycles on every path, and took 151 〔stella-list `200303/msg00152`〕. Its ball test `BCS DrawBall2` branched to the drawing arm; the skip arm fell through and padded itself with `SLEEP 22`. Manuel Polik: *"here you are jumping to the branch that is already the slower one!"* … *"If you'd swap both routines and jump to the quick branch here, it should save you exactly one cycle!"* 〔`200303/msg00154`〕. Dennis Debro posted the swap — `BCC .skipBallDraw ; using bcc shaves off 1 cycle`, the skip arm moved elsewhere and jumping back 〔`200303/msg00153`〕 — and Thomas Jentzsch put it as *"move the code after BCS DrawBall2 behind JMP X3. This will save you one cycle in the timing critical path"* 〔`200303/msg00155`〕: one cycle described three ways, not three cycles (our reading). From the posted counts both arms cost 32 cycles from the branch on; after the swap the drawing arm costs 31, and the skip arm, now entered by a taken branch and left by its `JMP`, matches it with `SLEEP 20` — Debro's version still has `SLEEP 21` (our count, no page crossing). Asked how the moved arm gets back, Polik: move it *"somewhere else and execute the return jump also in the quicker branch"* 〔`200303/msg00159`〕. Zavagli reported it solved without saying which version he kept 〔`200303/msg00157`〕. **Cited only, not verified.**

## 7. One extra cycle for no extra byte: a zero-page access indexed by a known X
When X holds a known constant, bias the address by it: `ldy zp,X` is 2 bytes / 4 cycles against `ldy zp`'s 2 bytes / 3 cycles (`definitions.json`: `$B4`, `$A4`).
```
ldx #LEFT_2                ; 2
ldy ts_loopCount-LEFT_2,X  ; 4 — reads ts_loopCount, one cycle later than `ldy ts_loopCount`
```
Omegamatrix: *"taking advantage of the X register if has a known value. You can easily add 1 cycle delay to the code when storing zeropage"* 〔AtariAge `topic/354058`〕. `design-principles.md`'s `sta.wx HMP0,x` buys a cycle by forcing absolute,X, which costs one more byte; this costs none but pins X. **Cited only, not verified.**
- **Not through a TIA mirror.** Chris Wilkson suggested stretching `sta GRP0` by a cycle through the mirror at `GRP0+$100`; Andrew Davie: *"You don't need to use the mirror, just sta.w GRP0 will do the job"* 〔stella-list `200102/msg00154`, `200102/msg00159`〕 — both make the store absolute, 3 bytes / 4 cycles (`$8D`). Where the store is to HMxx, HMOVE or HMCLR — the only registers `timinglint`'s rules look at — prefer `.w` for a second reason: it treats a store operand of `$80` or above as not a TIA write (`internal/cyclebound/timinglint.go`, `storeTIA`), so such a write through a `+$100` mirror is invisible to it. A `GRP0` store is checked by neither form. **Cited only, not verified** for the timing; the lint behaviour is read from its code.

## 8. A branch that will not reach
DASM stops with `error: Branch out of range` (exit 3, measured — `internal/build/build.go`). Three fixes, from three independent replies in 1999:
1. **Invert the condition and `JMP`**: `bne TooFar` becomes `beq Next / jmp TooFar / Next:` 〔stella-list `199901/msg00016` Robin Harbron, `199901/msg00020` Eckhard Stolberg〕.
2. **Branch to a nearby trampoline that holds the `JMP`**: *"it may seem a bit sloppy, but it's an easy way to get more distance out of a branching command"* 〔`199901/msg00017` John Harvey〕. One trampoline can serve many branches — Thomas Jentzsch's size fix for Climber 5: *"replace all but one jmp OverscanWait with branches and branch to the remaining jmp"* 〔`200304/msg00193`〕.
3. **Move code** so the target comes within range: *"This happens a lot when you have no idea where to place all the subroutines"* 〔`199901/msg00017`〕.

What 1 and 2 cost depends on how often the branch is taken, so no single cycle figure is given. **Cited only, not verified.**

## 9. A read-modify-write on a strobe also reads the input at the same address
TIA decodes reads by the low 4 bits, so `$2B` is HMCLR when written and INPT3 when read (`roms/litmus/litmus_floatbits.asm`). vdub_bobby's `asl HMCLR` (2 bytes, 5 cycles) strobes HMCLR and shifts INPT3's D7 into carry, replacing `sta HMCLR / sec` (3 bytes, 5 cycles) 〔AtariAge `topic/74034`〕. The strobe half is measured in this engine for `lsr HMCLR` (`internal/emu/floatbits_test.go`); `asl` is **not verified**.
- ★The carry is only as good as INPT3's D7, a paddle input. Asked whether it can be counted on if VBLANK D7 is never set, supercat answered only *"I wouldn't"*. He also advised against the `lsr` form (D0, a floating bit), and there he gave reasons: bus capacitance, crosstalk, selector boxes, ribbon cables 〔same〕.

## 10. Negating a byte: `eor #$FE` is right only for odd numbers
Found in Climber 5's source as *"make the number negative"*: for even n it gives −n−2 (`2 eor $FE = $FC = -4`) 〔stella-list `200304/msg00193`, Thomas Jentzsch〕. Andrew Davie's two correct forms 〔`200304/msg00201`〕:
```
lda number / eor #$FF / clc / adc #1
sec / lda #0 / sbc number
```
★A bug that survives every test written with odd values. The arithmetic was checked over all 256 byte values when this was written (all 128 odd values right, every even value off by −2). **Not verified** in a ROM.
- **254 − x needs no RAM temp.** For B with A + B = 254, Andrew Davie's `sec / lda #254 / sbc value` needs `value` in memory. Thomas Jentzsch then offered the negation (`eor #$ff / clc / adc #1`) and Davie stopped it — *"That negates a value. That's not what was asked for."* — and Omegamatrix gave `eor #$FF / sec / sbc #1`, which stays in A and *"saves a byte of ram and 1 cycle over subtracting using a ZP ram location"* 〔AtariAge `topic/316989`〕. Davie: *"assuming you have the value in the accumulator to start with. That's cheating"*; Jentzsch: *"your code assumed the value in a variable."* Both are right: 6 cycles against 7 (5 bytes each) holds only when the value starts in A; read from RAM, the `eor` form needs `lda zp` first and is 9 cycles, 7 bytes against Davie's 7 cycles, 5 bytes (`definitions.json`: `$A5`, `$49`, `$38`, `$E9` against `$38`, `$A9`, `$E5`). The formula was checked over all 256 values (decimal mode off); **Not verified** in a ROM.
- **Two bytes: subtract from zero.** Andrew Davie, 2004: *"for two-byte negation, easiest is to subtract the number from 0"* — `sec / lda #0 / sbc var / sta var / lda #0 / sbc var+1 / sta var+1`, the borrow passed from the low byte to the high 〔stella-list `200402/msg00020`〕; 13 bytes and 18 cycles with `var` in zero page (our count; `$38`, `$A9`, `$E5`, `$85`). The same post gives the one-byte form as `clc / lda var / eor #$FF / adc #1 / sta var`. Checked over all 65536 values (decimal mode off); **Not verified** in a ROM.

## 11. "More than one bit set?" in 8 cycles
`b & (b-1)` clears the lowest set bit, so it is non-zero exactly when b has two or more bits set (crispy). zackattack's version with unofficial opcodes 〔AtariAge `topic/280264`〕:
```
lax Input   ; 3  A = X = b
dex         ; 2  X = b-1
sax Output  ; 3  Output = A AND X
```
- ★Input 0 gives 0, which is the right answer to "more than one bit?". mldb first called it a false positive, then withdrew: *"I misread the assignment. I thought it said: if a single bit is set"* 〔same〕. So a zero result means "zero or one bit"; test 0 separately only if the question is "exactly one bit".
- `LAX`/`SAX` are in the family stable on real hardware, where "real hardware" means original NMOS silicon, and a reimplementation such as the Flashback 2 is reported to fail other illegal opcodes (`design-principles.md`, *Stability map for illegal (unofficial) opcodes*). The formula was checked over all 256 values; the code is **Not verified**.

## 12. A one-byte index where a two-byte pointer or a raw PF byte would go
- **Sprite pointers.** Nukey Shay on *Alien*: *"That game uses a single byte for each sprite as a pointer to 2 page long data tables. Slower than (ind),y but more Ram efficient. Another drawback is that sprites car [sic] limited to that 512-byte range"* 〔AtariAge `topic/291287`〕 — asked by someone spending 28 bytes of RAM on 14 pointers with the same high byte. **Cited only, not verified**: one byte reaches 256, and how the second page is reached is not in the thread.
- **Playfield maps.** nanochess, for a vertical scroller: use a mirrored PF so only PF0/PF1/PF2 change, and make each map line *"a single byte in map pointing to a table where to load the PF registers. So each line in your map would use one byte and you could make very long maps"* 〔AtariAge `topic/267694`〕. The byte is an index to a PF triple, not PF data as in the PF0 table below. **Cited only, not verified** — a suggestion, not a shipped kernel.

## 13. Macros: the seams, and the layout they can generate
- **Seams.** Thomas Jentzsch: *"You can save 4 cycles (TAY/TYA) when you call consecutive macros like e.g. Y_POS_ADV and X_POS_GAN"* 〔AtariAge `topic/263329`〕 — presumably (our inference, from TAY + TYA = 4 cycles) a register save and restore that cancel at the join. ## 14. When nothing else fits in 76 cycles: code in RAM
Thomas Jentzsch on the score and timer display of *Boulder Dash* 2600: *"we used self modifying code in RAM. The harness detects self-modifying code (`defuse`'s `writes_into_code`; `capability-gap-audit.md`, *Self-modifying code is detectable even when not resolvable*) but has no example of writing it. **Cited only, not verified** — the post does not say what was patched.

## 15. Count down to zero, and the decrement is the loop test
Kernels store art bottom row first because they index it with a counter that runs down. The reason given for running it down: `DEY` sets Z and N itself, so `dey / bne loop` (or `bpl`, to include row 0) needs no compare, where counting up needs `iny / cpy #rows / bne loop`. The compare is `CPY #` — 2 bytes, and 2 cycles on every pass (`definitions.json`, `$C0`). Glenn Saunders, finding the upside-down data confusing: *"it seems to be the standard way to do it on the 2600, having all the data upside down, probably because BNE is a quicker way to end a loop than testing for a given maximum value"* 〔stella-list `200109/msg00210`〕. `score-kernel.md` and `vertical-positioning.md` state the bottom-up order without this reason. §5 keeps a compare (`EOR #` for `CMP #`) and gets A = 0 from it. The *"probably"* is his; **Not verified** — no kernel was timed for this.
- **Outside the kernel too, and the reload value stays in A.** A clock of frames, seconds, minutes and hours was posted with a compare at every stage 〔stella-list `199710/msg00014`〕. Erik Mooney first rewrote it to increment, compare and store with 0 kept in A for the clears, then: *"If you can modify it so it counts DOWN to 0 for each value, it becomes much more simpler again"* — `dec FRAMES / bne DoneClock / lda #60 / sta FRAMES / dec SECONDS / bne DoneClock / sta SECONDS ;A was already 60 so no need to reload it`, and so on to hours 〔`199710/msg00016`〕. Chris Wilkson posted the same shape with `LDA #60` ahead of the first `DEC` 〔`199710/msg00017`〕. The price came next: Piero Cavina, of Wilkson's version, *"it counts seconds, minutes and hours in hex and this means a conversion to BCD in case you want to display it"* 〔`199710/msg00027`〕, and decimal mode does not rescue `DEC` — Mooney: *"In decimal mode, DEC still decrements $10 to $0F. You could load the value into A and do a SBC #1"* 〔`199710/msg00047`〕. **Cited only, not verified.**
- **Rotate the loop so the decrement sits just before the branch.** Thomas Jentzsch's Thrust score loop decremented at the top and closed with `tya / bne`, the `tya` there only to set Z 〔stella-list `200008/msg00024`〕. Andrew Davie: jump *"to the end of the loop on the first iteration, then you don't have to have an extra "tya" just to set the Z flag"* — enter with `jmp .digitEnd`, close with `.digitEnd: dey / bpl .digitLoop` 〔`200009/msg00018`〕. Jentzsch's reply is the counterweight: in that kernel the cycles were spare and the value wanted — *"2 cyles in reserve, which i'm wasting with the tay at the end of the loop (y = 0, i need that value to reset some TIA registers just in time)"* (the code has `tya`) — and Davie's rewrite was by his own account *"logical (but not functional or timing)"* 〔`200009/msg00044`〕. **Cited only, not verified.**
- **No `CPY abs,X`.** To stop at block boundaries kept in a table, so band heights need not be powers of two, Thomas Jentzsch's loop counts Y and tests `tya / cmp BlockSizeTbl,x / bne` 〔AtariAge `topic/66378`〕. `CPY` has only immediate, zero-page and absolute forms (`$C0`, `$C4`, `$CC` in `definitions.json`), so the compare goes through A: `TYA` adds 1 byte and 2 cycles, and A is lost (our count). **Cited only, not verified.**
- **A table of boundaries instead of a counter per block.** Kirk Israel's two-line kernel had no room for its per-block counter — `DEC scanlineInPFBlock / BNE`, a reload, `INC counterPFBlock` and two PF fetches 〔stella-list `200309/msg00139`〕. Thomas Jentzsch, as in his *Jammed*: *"Instead of counting scanlines for each PF-block I am simply counting down the total scanlines and compare those with values from a precalculated table"* — the bullet above's compare, with X as the counter (*"no cpx abs,y, too bad! :-("*). One state byte is left, and a line that is not a boundary only compares. His counts: the old code up to 34 cycles plus 5 for `dex / bne`, 39; his first version 18/35; with the change moved into a block before the loop that is entered by `beq` and falls back into it, 18/33 〔`200309/msg00144`〕. **Cited only, not verified** — the counts are his.
- **Zero and minus one from one `DEC`.** Thomas Jentzsch, for the background-colour counter `banda` in a first demo: start it at `#$0f` and count it down, and *"When decreasing banda you can test for -1 very fast too. So you have to easy testing values"* [sic] *"Now you can use zero for updating the color variable and -1 for resetting banda to #$0f"* — `dec banda / beq f2 / bpl f1 / lda #$0f / sta banda / jmp f2`, *"a maximum of 17 cycles (12 cycles saved)"* 〔stella-list `200105/msg00114`〕. `DEC` sets Z and N together, so one decrement branches three ways. The asker ran it and had to change that `jmp f2` to `jmp f3` 〔`200105/msg00117`〕. **Cited only, not verified.**
- **A table that steps and tests at once.** Andrew Davie, for an index that steps by 6: `txa / clc / adc #6 / tax / cpx #24 / bcc LOOP` costs 9 bytes and 13 cycles a pass; counting down, `txa / sec / sbc #6 / tax / bcs LOOP` costs 7 and 11; then `LDA #24` before the loop and `LOOP: TAX` … `LDA NEXT-6,X / BNE LOOP`, with `NEXT .BYTE 0,1,2,3,…` — one indexed load does the subtraction and sets Z for the exit, 6 bytes and 9 cycles, the data read as `MYVARIABLE-6,X` 〔stella-list `199805/msg00108`〕. His totals for 32 passes are 417, 353 and 289 cycles, *"a 30% speedup, by my calculations"*. Every loop can share the table, which must reach the largest index (same post). `LDA abs,X` adds a cycle where `NEXT-6+X` crosses a page (`$BD`, page-sensitive in `definitions.json`; our reading). **Cited only, not verified.**
- **Or let the data end the loop.** A table can carry its own end marker; `dynamic-multisprite.md`'s 0 sentinel is chosen by hand. memberatarian's Wavetari, a Windows tool that turns sampled sound into 2600 ROM data, chooses it from the data: after an "EndPoint" approach did not work, it generates all 256 byte values and takes one that does not occur in the table as the end byte 〔AtariAge `topic/298498`; held here only as distilled notes, so the wording is not checked〕. **Cited only, not verified** — the playback loop is not in the notes.

## 16. Counting the set bits in a byte
trogdor needed the number of set bits across 28 bytes for *Stellar Fortress*. Forms posted in the thread 〔AtariAge `topic/90828`〕:

| form | cycles | bytes |
|---|---|---|
| 8 × `lsr / bcc + / iny`, total left in Y (trogdor) | 50 worst | 34 |
| `sta Temp / lda #0`, then 8 × `lsr Temp / adc #0` — no branch (djmips, fixed by vdub_bobby) | 61 always | 36 |
| each nibble looked up in a 16-byte table (trogdor) | about 38 | 39 |
| `PLA` plus a half-byte table, with the illegal `ALR` (supercat) | "about 30" as reported in the thread; not recounted | — |

djmips also posted the mask-and-add fold (`and #$55`, then `#$33`, then `#$0F`), with no count. The first two rows agree with `definitions.json` (`$4A`, `$90`, `$C8` plus a leading `ldy #0`, `$A0`; `$85`, `$A9`, `$46`, `$69`) when no branch crosses a page, and the second was checked over all 256 values with decimal mode off. A 256-byte table would be 6 cycles and was turned down as 1/16 of a 4K ROM. supercat's 16-byte table leaves gaps where other tables can nest (used in Strat-O-Gems for a packed gem-to-colour conversion). jbanes' point comes first: if the program sets the bits itself, keep the count as it sets and clears them. §11 answers the cheaper question, "more than one bit?". **Cited only, not verified.**

## 17. Branch into an operand
`design-principles.md` has Omegamatrix's 8-byte init, in which `bne .loop+1` lands on the immediate operand `$0A` and runs it as `ASL` (*Minimum-byte initialisation*). The same move makes a 5-byte delay of 62 or 63 cycles 〔AtariAge `topic/354058`〕:
```
lda #$0A        ; $0A = ASL
pha
bne *-2         ; tracks guy: 5 bytes, 63 cycles, 8 bytes pushed

lda #$2A        ; $2A = ROL
.loop: asl
bne .loop-1     ; Omegamatrix: 5 bytes, 62 cycles
```
The second touches no stack: *"When the code below is done A=0, Carry is clear, and X and Y are preserved."* Both counts were stepped through with `definitions.json` cycles (`$A9`, `$0A`, `$2A`, `$48`, `$D0` 2 / 3 taken), assuming the branch stays in its page. **Not verified** in a ROM.

## 18. `PLA` reads and advances: the stack pointer as a table index
Replying to someone with no room in the line for `INC palettePtr` (5 cycles, `$E6`), Omegamatrix: *"In these situations I often store one of the digits in ram, and then use PLA to fetch it in the loop. It saves many cycles as you don't have to store to a TEMP variable in the loop"* 〔AtariAge `topic/215618`〕. A later post of Omegamatrix's adds: *"PLA will naturally increment the stack pointer. Use TSX and you can then index your color table. You can place the color table in rom."* `PLA` is 1 byte / 4 cycles (`$68`), `TSX` 1 byte / 2 cycles (`$BA`). The price is SP: it ends each frame somewhere else and needs a `TXS` to put it back (the asker: *"those TXS are ugly but it works"*). `design-principles.md` borrows SP as a spare colour register and `missiles-bullets.md` points it at ENAMx for `PHP`; here it is a read pointer that the fetch advances. **Cited only, not verified.**
- **SP as a temp for X: a fixed cost spread over uses.** Christopher Tumber counted one swap and found the stack pointer not worth it; Sean M.: *"The magic word is "amortize""* 〔stella-list `200405/msg00074`, `200405/msg00077`〕. Per use, `STX zp … LDX zp` is 6 cycles / 4 bytes and `TXS … TSX` 4 / 2, but the SP form first pays `TSX / STX zp` and `LDX zp / TXS` to keep the stack pointer, 10 cycles / 6 bytes; it draws level on bytes at three uses and on cycles at five (our count; `$86`, `$A6`, `$9A`, `$BA`). Sean's listing sets three zero-page pairs (18 cycles, 12 bytes) beside two SP pairs plus that save and restore (18, 10), so its break-even compares unequal counts. Paul Slocum: at top level there is nothing to save — set SP back to `$FF` afterwards 〔`200405/msg00078`〕 — and the fixed cost falls to `LDX #$FF / TXS`, level on cycles and a byte ahead from the second use (our count). **Cited only, not verified.**

## 19. Keep the loop counter in RAM to free X and Y
glurk, for someone trying to fit ten `COLUPF` changes into each line: *"I used a RAM variable as the counter, and used X and Y registers as needed. It reads the colors from $90-$99 and makes a 10-color rainbow thing"* 〔AtariAge `topic/346865`〕. The counter then costs `DEC zp` (2 bytes, 5 cycles, `$C6`) where `DEY` costs 1 byte and 2 cycles — 3 cycles a pass (our arithmetic), with the branch still reading Z from the `DEC` — and both index registers are free for the line. **Cited only, not verified** — the demo was not read.
- **The price when it is not chosen.** Adam Wozniak's maze kernel loaded its first three PF bytes with `lda` and the last three with `ldx`, so the row counter it kept in X had to go through `tmp2`. Christopher Tumber: *"If you stuck with lda Maze,y throughout, you can use X as your loop counter without having to store it to RAM. This will save you 6 cycles in the MazeRowLoop and 3 cycles in MazeRow"* — the `ldx tmp2` / `stx tmp2` around the loop's `dex`, and the `stx tmp2` before the loop 〔stella-list `200301/msg00008`〕. **Cited only, not verified.**

## 20. A subroutine's final `RTS` is a 12-cycle delay
SpiceWare's positioning routine ends `SLEEP12: rts`: *"That SLEEP12 label at the end is used for wasting 12 cycles by doing a jsr SLEEP12"* 〔AtariAge `topic/233692`〕. Any subroutine's closing `RTS` already is one; the label only names it. The cost — 12 cycles, 3 bytes — is the row `jsr` + shared `rts` in `known-traps.md` (*The delay table, measured*), measured in this engine by `internal/emu/delaytable_test.go`; the call also uses two bytes of stack, which that test does not check.
- **A ladder of entry points.** Manuel Polik: *"jsr to any subroutine point wasting the desired # of cycles"*, with `Waste16: NOP / Waste14: NOP / Waste12: RTS` 〔stella-list `200210/msg00167`〕 — 3 bytes at each call site, and each `NOP` above the `RTS` adds 2 cycles for 1 shared byte (our count). Christopher Tumber's variable form jumps through `jmp ($ZeroPage)` into a run of NOPs 〔`200210/msg00169`〕; Thomas Jentzsch had used it in his TomInv demo and suggested `NOP zp` or a taken branch to reach odd counts 〔`200210/msg00173`〕. **Cited only, not verified.**
- **Entry points are not only for delays.** Glenn Saunders: *"You can seek into and JSR into any line of a subroutine you want"*, and *"An example of where this is used is in Manuel's horizontal positioning subroutine. It seeks to a different startpoint for P0 vs. P1"* 〔stella-list `200110/msg00435`〕. Erik Mooney: *"assembler is inherently so because every instruction has an address"* 〔`200110/msg00438`〕. The price is reading — Glenn's complaint was that a label does not say whether it is an entry. Thomas Jentzsch's answer: DASM's `SUBROUTINE`, local labels starting with `.`, *"Only the subroutine labels and the extra startpoints get a normal name without the point"*, and a comment header giving each routine's input and output registers, variables and flags 〔`200110/msg00440`〕; Chris Wilkson numbers the insertion points, `FOO_start`, `FOO_001` 〔`200110/msg00439`〕. The positioning routine is not in the thread. **Cited only, not verified.**
- **A caller that repeats the entry it skips.** Thomas Jentzsch, from a DiStella listing of Andrew Davie's *Qb*: `LDA #$08 / JSR LFA60` … `LFA5E: LDA #$08 / LFA60: STA $E8` — the caller loads the value the routine's own first instruction loads, then calls past that instruction — *"And this happens more than once :)"*; and `LDX #$00 / LDA #$00` 〔stella-list `200102/msg00346`〕. He does not spell out the fixes; calling `LFA5E` drops the caller's `LDA #$08`, 2 bytes a call, and `TXA` replaces the second load, 1 byte (our reading). Davie held both back: *"They both create a dependency between the code and values used for creature types. Not a serious dependency, but these things are to be avoided until the last possible moment"* 〔`200102/msg00349`〕. **Cited only, not verified.**

## 21. Initialise the top of RAM by pushing
jeremiahk found the bytes for music in his 512-byte demo *Acid Rain* by *"Putting values at the end of RAM so they can be initialized by pushing values on the stack"* (tjoppen's words) 〔AtariAge `topic/280442`〕. After a clear that leaves SP = `$FF` (the 8-byte init in `design-principles.md` does), `lda #v / pha` writes `$FF`, then `$FE`, and so on; `PHA` is 1 byte where `STA zp` is 2 (`$48`, `$85`). The variables then sit above SP, where later `JSR`s do not reach them (our reading). **Cited only, not verified** — the demo's source was not read.

## 22. Transpose the playfield buffer so every column shares one Y
Mr SQL's kernel read one line's six PF bytes from consecutive RAM — `lda $00A0,y / sta PFn / iny`, six times (PF0, PF1, PF2, then again) — and on each repeated line rewound Y with `tya / sec / sbc #$06 / tay`. Tjoppen: *"You should store the data transposed in RAM, so you can access each column of playfield with the same Y value"* 〔AtariAge `topic/203463`〕 — six tables `PF0DataL` … `PF2DataR`, each read `,Y` with the same Y, which takes six `INY` (12 cycles) and the 8-cycle rewind out of the line; he estimated *"20-25-ish cycles to spare"*. The price is the layout: Mr SQL's buffer engines wrote row by row, and transposing without rewriting them would have cost 30 more bytes of RAM. §3 folds a constant offset into a pointer; this folds a stride into the layout. **Cited only, not verified.**

## 23. The line counter's low bit as a draw/logic switch
ScumSoft gives alternate lines to drawing and to game logic by the low bit of the line counter 〔AtariAge `topic/178066`〕:
```
PF_LOOP:   tya
           eor #1
           and #$01
           beq PF_LOGIC   ; odd Y: logic, with the graphics blanked
           ...            ; even Y: draw
PF_Return: dey
           sta WSYNC
           bne PF_LOOP
```
In overscan a toggled byte starts Y at 191 on one frame and 192 on the next, so the two sets of lines trade places each frame, and `TIM64T` gets 33 or 34 to hold 262 lines (his comments). He calls it interlaced; it is not TV interlace (`design-principles.md`: true interlace is not in this repository) — each line is drawn every other frame (our reading; he says *"I find this gives minimal flicker"*). `eor #1` only inverts the test: `tya / and #$01 / bne PF_LOGIC` takes the same branch in 2 fewer bytes and 2 fewer cycles (our reading). Three days later ScumSoft withdrew it: *"never mind the first post here, I found a much better way to interlace the frames. Much of that code was not really needed at all"* 〔same〕; that post does not show the better way. **Cited only, not verified.**

## 24. Spare bits on the input side
§1 packs data into register bits the hardware ignores; the same move works on what the program reads.
- **SWCHB's unused bits as storage.** omegamatrix: *"There are actually 3 bits in SWCHB that are free"* — `lda #$34 / sta SWBCNT` makes D5, D4 and D2 outputs, *"Then you can read and write to SWCHB like a normal register"*. svolli: it *"only works on port B, while port A (SWCHA) may be affected by the controllers even when the pins are set to output"*. groovybee: never make a bit wired to a console switch an output — a difficulty switch in B *"will connect the corresponding RIOT pin directly to ground"*, and driving a 1 into it *"isn't good for RIOT"* 〔AtariAge `topic/197100`〕. Combat sets D4 alone as an output at start-up (`fundamentals-audit.md`, *SWACNT/SWBCNT DDRs*, decoded from its bytes). **Cited only, not verified** — no ROM here keeps data in SWCHB.
- **An impossible combination as a code.** Christopher Tumber, sizing a recording of joystick moves: *"you'll never have Up+Down+Right+Left so 1111 can be jump and you're down to 1 nibble"* for the directions, plus a frame count 〔stella-list `200410/msg00103`〕. "Never" is a property of the controller: `known-traps.md` (*Opposing joystick directions cannot be tested here at all*) records controllers that close opposite directions and an engine that cannot produce them. **Cited only, not verified.**
- **Fold a second input into bits the game does not read.** Omega Race, as Thomas Jentzsch disassembled it: `lda SWCHA / and #$cc` (*"clear up and down bits"*), then the two Booster Grip buttons, read on INPT0 and INPT1, are ORed in as `#$10` and `#$20` (*"fire button is also an option here"*), and the same is repeated for the other port 〔stella-list `200202/msg00146`〕. A ends holding the stick's remaining bits and both buttons; what the game does with it next is not in the post. **Cited only, not verified.**
- **Shift the stick out a bit at a time, and keep A.** `lda SWCHA` then four `asl / bcs`, each skipping one direction's handler, reads all four directions, diagonals included, from one load — Erik Mooney's correction of a version that could take only one direction 〔stella-list `200207/msg00268`〕. Earlier, on that original `asl / bcc` version, Thomas Jentzsch: *"You can save one more byte (the first ASL) if you use BPL instead of BCC"* 〔`200207/msg00266`〕 — testing N instead of C drops the first `asl` from Mooney's chain the same way (our reading). Mooney's condition is that the handlers run *"without changing A"*; otherwise `STA TempVar / ASL TempVar`, one byte of RAM. This repository has both shapes: `roms/techniques/rpgmap.asm` uses the chain (its handlers only `inc`/`dec`), `roms/exerciser/exerciser.asm` reloads `SWCHA` before each `and #mask / bne` — 15 bytes against 28 for the four tests (our count). **Cited only, not verified.**
- **"Is the stick centred?" in two instructions.** Ruffin Bailey tested player 0's four direction bits with `lda SWCHA / and #%11110000 / eor #%11110000 / beq` 〔stella-list `200207/msg00271`〕. Thomas Jentzsch: *"A minimal improvement would be (saves 2 bytes)"* — `lda SWCHA / cmp #%11110000 / bcs dontIncreaseFrame ; CF=1, if all 4 upper bits are set` 〔`200207/msg00272`〕. A is `$F0` or more exactly when D7-D4 are all 1, nothing pressed, whatever the low nibble holds, so player 1's bits need no mask; it also saves 2 cycles (`$29`, `$49` against `$C9`, all 2 bytes / 2 cycles; our count). **Cited only, not verified.**

## 25. Byte savings outside the kernel
Thomas Jentzsch's list for *Space Treat*, its ROM almost full, all of it game logic 〔stella-list `200212/msg00349`〕:
- a `CMP #1 / BEQ … CMP #4 / BEQ` dispatch: *"reversing the order and using DEX/DEY"*;
- repeated code → a table and a loop;
- `JSR somewhere / RTS` → `JMP somewhere`, *"save one byte"* (the tail call, below);
- `LDA #0` after a branch that falls through only when A is already 0 — drop it;
- `LDA SWCHB / AND #%00000001 / BNE` → `LSR / BCS`, one byte (he gave the same rewrite for *M-4*'s `lda Counter / and #1 / bne` 〔`200505/msg00030`〕; Jim Nitchals had pointed out `and #1 / beq` → `lsr / bcc` in *Combat*, where *"the code doesn't need to preserve the accumulator or the carry flag"* 〔`199703/msg00048`〕);
- `LDA v / CLC / ADC #1 / STA v` → X or Y, two bytes. Manuel Polik: *"maybe because it's BCD?"* — `INX` ignores decimal mode — and if not, `INC v` 〔`200212/msg00352`〕; the author was not using BCD 〔`200212/msg00359`〕;
- `CMP #10 / BNE / LDA #0 / STA` → `EOR #10 / BNE / STA` (§5);
- `JMP` → a branch that is always taken there (`branch-always.md`);
- load with X or Y so a 0 already in A can be stored again;
- `LDA v / CMP #W / BEQ / LDA #W / STA v` → `LDA #W / CMP v / BEQ / STA v`;
- have a subroutine return the value its callers load again.

**Load in the arms, store once.** Jentzsch's next rewrite for *M-4*, Bob Montgomery's port aimed at 1K: the black-and-white arm (`lda #WHITE`, three `sta`, `jmp DoneSettingColors`) and the colour arm (four `lda #` / `sta` pairs) become arms that only load — `lda #WHITE / tax / tay / bne DoneSettingColors` on one side, `ldx #CACOLOR / ldy #TANKCOLOR / lda #WALLCOLOR` on the other, each still storing `GroundColor` itself — and one shared tail `stx CarAirplaneColor / sty TankColor / sta COLUPF` 〔stella-list `200505/msg00030`〕. The `bne` is always taken only while WHITE is not 0 (our reading; `branch-always.md`). With every store in zero page, 29 bytes become 24 (our count). **Cited only, not verified.**

**The tail call.** Besides that byte it saves 9 cycles — JSR 6 and RTS 6 against JMP 3 (`$20`, `$60`, `$4C`) — and the 2 bytes of stack the return address would hold while the callee runs 〔AtariAge `topic/118545`, seagtgruff and Nukey Shay〕. supercat put it as *"In most cases"*, and it saves a stack *level* only where that level was the deepest: in the thread's example the routine needed one anyway to call the other 〔same〕.

**Inlining a routine with one caller.** Dennis Debro, same thread: *"each jsr/rts costs you 4 bytes when you can just place the routine where it's needed"* — JSR 3 + RTS 1 — said of the main loop of Nick's *How To Draw a Playfield*, an outline *"great to get started"* 〔`200212/msg00354`〕. That saving is for a routine with one call site (our reading). **Cited only, not verified** — none of this section was assembled here.

## 26. Let the colour follow the graphics: `SAX COLUP0`
eshu's costs for one sprite line 〔AtariAge `topic/136387`〕: `LDA Sprite,y / STA GRP0` 7 cycles; with `AND Mask,y` 11; SkipDraw more. A colour of its own is another `LDA Colour,y / STA COLUP0`, 7. If the colour may depend on the graphics, `SAX COLUP0` after the `AND Mask,y` adds 3: SAX stores A AND X (`$87`, 2 bytes / 3 cycles, undocumented), so COLUP0 receives the masked graphics byte ANDed with X instead of a value from a table of its own. What X holds is not shown. `SAX`'s stability is as in §11. **Cited only, not verified.**

## 27. A counter modulo 3 with no branch
```
lda index
cmp #2      ; C = 1 only when index >= 2
adc #1      ; +1, or +2 when C is set
and #3      ; 4 becomes 0
sta index
```
0→1, 1→2, 2→0; the three middle instructions are 6 bytes and 6 cycles on every path 〔AtariAge `topic/319926`〕. Checked by hand for 0-3: a stray 3 also lands on 1, so the counter cannot stick outside 0-2. A power-of-two period needs only the `AND`. **Cited only, not verified** in a ROM.

## 28. Two 4-bit characters into one byte
To show 12 characters a line from six bytes, each byte holds two characters 4 pixels wide. Piero Cavina proposed a font with each character twice in its byte (`%01000100` for a row of "A"), so nothing has to be shifted; Greg Troutman priced it at *"one mask operation (2 cycles) vs. 4 ASLs (8 cycles), or a savings of 6 cycles per byte"* 〔stella-list `199709/msg00311`〕. With the AND-then-OR combine he counts, one mask is not enough: the unmasked byte's other nibble lands on top of the masked one, and over all 256 pairs of 4-bit characters ORing one masked byte with one unmasked byte is wrong for 175. Both need a mask, 4 cycles against 8, saving 4 cycles a byte (our count). The thread's own answer drops the mask altogether — Jim Nitchals: *"If you use two font tables, you can skip the mask"*; Erik Mooney: *"LDA character1 / ORA character2 / STA destination"* 〔`199709/msg00317`, `199709/msg00318`〕 — at the price of a second font. **Not verified** in a ROM.

## 29. Packing state into RAM
§1 and §24 put data into bits the hardware ignores; with 128 bytes, the program's own variables get the same treatment.
- **A counter's spare bits.** Ruffin Bailey slowed an animation with `adc #%00000100 / and #%00111100 / sta p0FrameCount` — *"I'm only wasting four bits of the byte"* 〔stella-list `200207/msg00288`〕. Thomas Jentzsch: *"actually you need five bits (the 6th bit is changed too) and therefore "waste" only three. :-) But if you write AND #%10111111 (and make sure that the carry is allways cleared before ADC), then you can still use the bits 0,1 and 7 for something else"* 〔`200207/msg00292`〕. With bit 6 cleared after every step, adding 4 carries at most into bit 6, and with C clear it leaves bits 0-1 alone (our arithmetic). **Cited only, not verified.**
- **A board's spare nibbles.** Answering a guess that Video Chess's 64 board bytes waste their spare bits, Eckhard Stolberg: *"The other bits aren't wasted. Video Chess uses the lower nibbles of those 64 bytes to store the 14 possible things that each field can contain"* (empty, six pieces in two colours, the marker), and *"I think the high nibbles for all the bytes are used for calculating the the next move. I din't try to figure out the algorithm though"* [sic] 〔stella-list `200006/msg00100`〕. The high-nibble use is his guess. **Cited only, not verified** — the cartridge was not traced here.
- **A path as moves, not points.** cpc464kid's Snakes stored each segment as one byte, 4 bits of X and 4 of Y on a 16×16 grid, about 75 segments. Andrew Davie: keep the tail and head positions and *"the body simply as a series of 'move directions'. Moves are only up/down/left/right, so you only need two bits. Thus, 4 positions per byte"*. The author then reported the playfield *"1/3 wider (24x16)"* and the maximum length *"more than double at 200+ segments"*. Davie's further idea — store nothing and follow the lit playfield pixels — the author turned down: *"I don't think it would be possible to find the adjacent set-pixel without storing all the movements"* 〔AtariAge `topic/308519`; held here only as distilled notes, so the wording is not checked〕. **Cited only, not verified.**
- **Setting bit N of a bit array.** danjovic's routine 〔AtariAge `topic/333278`; held here only as distilled notes, so the wording is not checked〕: divide N by 8 with a `sec / sbc #8 / bcc` loop that counts the byte index in X, turn the remainder into a count (`clc / adc #9 / tay`), shift `#$80` right that many times less one, then `ora _a,x / sta _a,x`. Bit 0 of the array is bit 7 of its first byte. Traced by hand for N = 0, 3 and 8; both loops make the cycle count depend on N (our reading). **Cited only, not verified** in a ROM.
- **A playfield in RAM: bitmap, packed, or a list.** Glenn Saunders: PF1 and PF2 alone are 4 bytes a line, *"80 bytes for a 32 pixel by 20 8-pixel-high bitmap of blocks. If you used 6 bytes per line, that would be 120 bytes right there"*, and *"128 bytes is barely enough to do playfield bitmaps"* 〔stella-list `200103/msg00028`〕 (his PF0 packing is in the PF0-nibble section at the end of this page). Erik Mooney took the other side for *INV*: *"six bytes per line, because there wasn't time in the kernel to do any additional processing for the PF0 nibbles"*, affordable with five playfield lines, 30 bytes 〔`200103/msg00032`〕. For a screen that is never full, Glenn weighed a list of up to 32 pixel indices in 32 bytes and doubted the kernel could decode it on the fly *"without sacrificing sprite logic on those scanlines"* — he meant to alter the missiles there 〔`200108/msg00357`〕. Manuel Polik's answer caps the count per row: four entries per row in a page-aligned table, an `empty` value filling the unused slots, read as `LDX level1,Y` then `LDA FX00,X` … `LDA FX00+3,X`, and he closes *"I think you'll see only in practice which idea is best"* 〔`200108/msg00370`〕. A fixed count makes the reads per row the same on every row (our reading); the tables as posted are ROM data (`ORG`, `.byte`), and what each entry becomes on screen is not shown. **Cited only, not verified.**

## 30. One cycle short, at one place in the line
Glenn Saunders, adding a RAM colour to Thomas Jentzsch's 3x2 multicolour score: the closing `stx.w GRP1` was *"happening one cycle too late!!"*, the kernel has no `WSYNC`, and he had *"nowhere else to shove a .w into to pad it by 1 cycle"* 〔stella-list `200508/msg00167`〕. The suggestions:
1. Manuel Rotschkar: remove the `.w` 〔`200508/msg00168`〕. Glenn: *"it breaks the kernel because the kernel relies on absolutely perfect timing (no WSYNC used)"* 〔`200508/msg00170`〕.
2. Christopher Walton: *"How about putting the .w on the first sta COLUPF instead, and then starting the loop on cycle 75?"* 〔`200508/msg00171`〕 — move the padding cycle rather than drop it (§7; `design-principles.md`'s `sta.wx HMP0,x`).
3. Fred Quimby: *"remove the .w but make sure the kernel crosses a page boundary so that the branch adds a cycle"* 〔`200508/msg00172`〕 — the cycle lands on the loop's closing branch, after the late store. Here the page-cross penalty is the tool; elsewhere in this repository it is the hazard (`hmove-two-step.md`: keep the ÷15 loop page-aligned). The rule itself, a taken branch across a page costs 4, is machine-locked by `TestPageCrossPenaltyRules` (`internal/cpudiff/pagecross_test.go`).
4. Thomas Jentzsch: *"I suggest unrolling the loop once to gain the missing cycles"* 〔`200508/msg00177`〕.

Glenn's own fix, posted before Jentzsch's message, was a reorder: `sta.w COLUPF` moved back to the top of the loop with its colour load above the loop, the stores rearranged, and a remaining 1-pixel fringe hidden — *"I squeezed the font together by 1 pixel! So now the display is rock solid"* 〔`200508/msg00174`〕. Jentzsch's reply to it: *"you removed one necessary write to GRP0 (VDELPx!). So the last digit of the 2nd and 3rd number are always the same now"* 〔`200508/msg00177`〕 — a picture that looked right with two digits forced equal. `litmus_48px6` (`verified-coverage.md`) compares all 48 bits against a design with a distinct byte per copy, the kind of check that tells those apart (our reading). **Cited only, not verified** — none of the four was assembled here.

**Between loops: one cycle, and no page crossing.** Andrew Davie chained tight loops copied block after block, each closing `dec LoopCount / bpl` with *"NO cycles free"*. The last pass of each falls through the `bpl` one cycle early, and *"The more of these blocks of code I put in, the more likely it is that one of those branches will end up having to branch over a page boundary"* — which is why he turned down a `.byte` that makes the next block's first `NOP` a 3-cycle instruction 〔stella-list `200301/msg00105`〕. His answer: each loop ends `jmp NEAT` with `ALIGN 256` before the next, and `NEAT` labels the second of the next loop's three opening `NOP`s — *"the jump + the remaining 2 nops gives 7 cycles which is (6+1) ie: we've added just one cycle for the first iteration of the loop only"*, while no loop's branch can cross a page. Here the page cross is the hazard (as in `hmove-two-step.md`), where suggestion 3 above used it as the tool; each `ALIGN 256` pays in ROM padding (`known-traps.md`, *bank-move misaligns code → page-cross*). **Cited only, not verified.**

## 31. When a table or a pointer does not reach
- **More than 256 entries.** Y is 8 bits, so `lda DATA,y` reaches 256 bytes; for a longer table the notes of this thread split the reads in two, without saying who proposed it: `lda DATA,y` for the first 256 and `lda DATA+$100,y` for the rest (300 entries: 256 + 44) 〔AtariAge `topic/339019`; held here only as distilled notes, so the wording is not checked〕. What a read across the page boundary does and costs is the `known-traps.md` row citing the same thread. **Cited only, not verified.**
- **Two pointers to arbitrary ROM addresses do not fold into one loop.** quohog wanted one loop over two sound blocks, each through its own pointer. `(zp),Y` uses one fixed zero-page pointer that X cannot choose; `(zp,X)` chooses by X but takes no Y (`$A1`, 6 cycles; our reading). Andrew Davie: where the pointers lead to arbitrary ROM addresses, keep the two unrolled blocks. Self-modifying code was raised and set aside: no speed gained, more ROM. A loop pays when the data can share one table (one pointer, each channel's index loaded into Y by X) or sits page-aligned (absolute,Y, no pointer in RAM) 〔AtariAge `topic/311300`; held here only as distilled notes, so the wording is not checked〕. **Cited only, not verified.**
- **Pointer set-up between rows, over budget.** karl-g's tile kernel set 12 graphics pointers between tile rows at 20 cycles each — `ldy sc_read+0,x / lda (TilePtrLow),y / sta G0Ptr / lda (TilePtrHigh),y / sta G0Ptr+1` — 240 cycles against the 228 of three lines 〔AtariAge `topic/298395`; held here only as distilled notes, so the wording is not checked〕. The options in the thread: narrow to 10 pointers (80 px); move the tile map from SuperChip RAM to zero page; give the gap a fourth line; preset the high bytes, which holds only while all tile graphics share one page (25 tiles of 10 bytes) — Omegamatrix pointed at the high bytes; or read the tile addresses from a table instead of through pointers, at the price of code and data per tile set. karl-g's answer was the direct read plus front-loading the display loop so its spare cycles gather at the end. Presetting the high bytes takes `lda (TilePtrHigh),y / sta` out of each set-up, 8 of the 20 cycles (our count; `$B1`, `$85`). **Cited only, not verified.**

## 32. Let the carry work
- **Fold the borrow into the constant.** Bob Montgomery's pointer set-up was `lda #<TankLDataa / sec / sbc TankLY / clc / adc #TANKHEIGHT / sta TankLPtra`; Thomas Jentzsch's rewrite is `lda #<TankLDataa / clc / adc #TANKHEIGHT+1 / sbc TankLY ; carry is always clear! / sta TankLPtra` 〔stella-list `200505/msg00030`〕. `SBC` with C clear subtracts one more, which the `+1` pays back; one flag instruction fewer, 1 byte and 2 cycles (`$38`; our count). The comment is the whole guarantee: C is clear after the `adc` only while `<TankLDataa` + `TANKHEIGHT` + 1 stays below 256, so the table's place in its page decides it (our arithmetic), and nothing here checks a comment against the flags. **Cited only, not verified.**
- **One compare for both edges.** Manuel Polik asked how to tell a value had gone below `$00` or above `$A0` 〔stella-list `200103/msg00100`〕. Thomas Jentzsch: *"Add $5f and check if the carry flag is set."* 〔`200103/msg00101`〕 — `$A0` + `$5F` = `$FF`, so 0-`$A0` add without a carry and anything above carries, including a step below 0 that now reads `$FF`, `$FE` …, as long as the step is under 96 (our arithmetic). Andrew Davie: *"-1, -2, etc... are represented in binary as $FF, $FE, etc.... which as unsigned numbers are > 160 (ie: you can use your right bound to determine BOTH a left/right bound overflow)"* 〔`200103/msg00103`〕 — the principle `vertical-positioning.md` uses for the skip-draw compare. Tim Böscke: *"Where is the problem with a CMP ?"* 〔`200103/msg00104`〕. Manuel said he would answer that in his reply to Davie 〔`200103/msg00105`〕; that reply gives his reason for asking — the sign test he used vertically fails for X, where *"any values from $80-$A0 would be in valid range, but already negative!"* — and does not mention `CMP` 〔`200103/msg00106`〕. `cmp #$A1` sets the same carry and keeps A (our arithmetic), and Davie's own clamp uses `cmp #$A0`. **Cited only, not verified.**
- **A carry the shifts already cleared.** Jim Nitchals on *Combat*'s ×5 of a score digit, `lda TheScore,X / and #$F0 / lsr / lsr / sta Temp1 ; * 4 / lsr / lsr / clc / adc Temp1 ; * 5`: *"The clc isn't needed because the least significant bit is already 0 from the and #$F0 instruction"* 〔stella-list `199703/msg00048`〕 — the two `lsr` before the `adc` shift out bits the `and` cleared, so C is already 0; 1 byte and 2 cycles (`$18`). Checked over all 256 values; **Not verified** in a ROM.
- **Touch the high byte only on a borrow.** Andrew Davie, reading a first homebrew: after `LDA plrClrPtr / SEC / SBC plrYpos / STA plrClrPtr`, the high byte's `LDA plrClrPtr+1 / SBC #0 / STA plrClrPtr+1` *"can be replaced by"* `bcs .nocarry / dec plrClrPtr+1 / .nocarry`, *"saving 2 bytes each time. similarly, any 16-bit adds use bcc/inc"* 〔AtariAge `topic/313575`; held here only as distilled notes, so the wording is not checked〕. In zero page the high byte then takes 3 cycles without a borrow and 7 with one, against 8 (our count; `$B0`, `$C6` against `$A5`, `$E9`, `$85`) — a time that depends on the data, so not a form for a line that must cost the same every time (our reading). The two leave the same two bytes in memory (checked by brute force), but not the same registers: A ends holding the low byte instead of the high one, and C, N and Z can differ (our reading); **Cited only, not verified** in a ROM.
- **Rotating without the carry.** `ROL`/`ROR` go through C (`known-traps.md`, *ROL/ROR rotate THROUGH the carry*). Jim Nitchals's ways to rotate A by itself 〔stella-list `199709/msg00252`〕: left, `asl a / adc #0` (*"move old bit 7 into bit 0"*); right, `lsr a / bcc .no_carry / ora #$80`; right and *"time-invariant (may be important in display routines) but slower"*, `sta temp / lsr a / lda temp / ror a`; and *"even slower and takes fewer bytes and is still time invariant"*, `pha / lsr a / pla / ror a`. They cost 3 bytes / 4 cycles, 5 / 5 or 6, 6 / 10 and 4 / 11 (our count, `temp` in zero page, no page crossing; `$0A`, `$69`, `$4A`, `$90`, `$09`, `$85`, `$A5`, `$6A`, `$48`, `$68`); the `adc #0` form needs decimal mode off. All four were checked over 256 values; **Not verified** in a ROM.
- **A byte with both nibbles alike.** Christian Bogey defined a PF0 shadow value as `#%11001100` *"so High and low Nybble are the same pattern"*, his answer to happy_dude's point that PF0 shows only its top nibble 〔stella-list `200404/msg00367`, `200404/msg00371`〕. A true 8-bit rotation of such a byte rotates each nibble by one bit, so the nibble PF0 shows keeps its 4-bit pattern moving (our arithmetic, checked for all 16 nibbles); his `ROL`s went through C instead — the `known-traps.md` row above. **Cited only, not verified.**

## 33. A playfield picture written in immediates
Jake Patterson's 2001 demo draws an asymmetric, multicoloured playfield illustration 〔stella-list `200109/msg00096`〕. Asked how many colours a line can take 〔`200109/msg00098`〕, he answered 〔`200109/msg00113`〕:
- **No time for tables.** *"there isn't enough time to load the different colors and playfield bitmaps from a table, instead, each set of six scanlines (there is also one set of twelve and one set of 24) has its own loop and the data is loaded "immediately" so it only takes five cycles to do a load and store instead of seven"* — `LDA #` is 2 cycles where an indexed read is 4 (`$A9`, `$BD`). The price: *"about 1000 lines of code for that one frame"*, *"probably more then 2k or so by itself"* [sic], and a picture that cannot change from frame to frame.

His count: *"nine carefully timed color changes per scanline, with up to seven different colors... but at the cost of it being static in nature"*. §5 gets A = 0 from a loop exit; here A is simply never reloaded in the loop.

He notes *"It has not been tested with real hardware, but it does function on Mac Stella"* 〔`200109/msg00096`〕. **Cited only, not verified.**

## Packing PF0's nibbles: +3 cycles a line, or +19 written the obvious way (2026-09-07)

PF0 uses only its high nibble, so a two-line pair fits in one byte. `design-principles.md` has the
extreme — *"not drawing PF0 … frees 12cy per line + 18 bytes of RAM"* — and this page has nibble
packing as a general idiom. The middle had no line anywhere, though Ben Larson was doing it in 2002
and finding it awkward: *"The fact that I'm **packing both PF0 nibbles into one byte** probably
doesn't help the situation"* 〔`200210/msg00045`〕.

Measured over four kernels (`internal/cyclebound/pf0nibble_test.go`), the last two unrolled across two
scanlines:

| kernel | Krow cycles |
|---|---|
| one line per iteration, one byte per line | 22 per line |
| one line per iteration, packed, parity tested at run time | 41 per line — **+19** |
| two lines per iteration, one byte per line | 11 + 22 = 33 per pair |
| two lines per iteration, packed, odd nibble via a table | 11 + 28 = 39 per pair — **+6, so +3 a line** |

★**The same idea costs +19 or +3 depending on how it is written** — a factor of six, because unrolling
removes the parity test entirely: the two halves of the pair know which nibble they are.

★★**The unrolled control is what makes that readable.** The first version of this measurement compared
a single-line unpacked kernel against an unrolled packed one, and made packing look *cheaper* than not
packing. The saving was the loop overhead halving and had nothing to do with nibbles.

★★★**What it buys and costs:** 16 bytes of RAM for a 32-line band, +3 cycles a line, 256 bytes of ROM
for the shift table. Against the extreme — abandoning PF0 *gains* 12 cycles a line and 18 bytes — so
packing is only the right answer when PF0's content is actually needed. Found by the mailing-list
distillation (helper-1).

**The other pairing: the two PF0s of one line.** Nick Bensema's 2002 scroll-text demo keeps the left
half's PF0 in bits 4-7 and the right half's in bits 0-3: *"since PF0 only recognizes bits 4-7, I used
bits 0-3 to contain PF0 data for the right side of the screen. The only downside to that is that
shifting those bits costs eight cycles per scanline, which could probably only be reduced to six by
using an AND, an indexed LDA, and a 16-byte lookup table"* 〔stella-list `200208/msg00020`〕. Glenn
Saunders had sketched it the other way round in 2001, the first PF0 in the low nibble, for a full-width bitmap of six bytes a line: *"store the
first instance of PF0 in the lower nibble and the second instance in the higher nibble, thus shaving
things down to 100 bytes, then somehow swapping the bits in mid-kernel"* 〔`200103/msg00028`〕. The
8 and 6 cycles are Bensema's estimate, not one of the kernels measured above. **Cited only, not verified.**
