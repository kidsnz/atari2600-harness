# Casebook — situation → technique (cases backed by disassemblies of real commercial games)

Where `cookbook.md` runs forwards — "**the game type you want to build → the standard recipe**" — this document is a **case catalogue** that runs backwards and is evidence-driven: "**how a real commercial game solved a given situation**". Every entry carries **situation → technique adopted → why it works → source (manual + disassembly author)**. It is the index to consult in the retrieve step of the authoring loop (`authoring-protocol.md`) when asking "how do real games solve this situation?".

> This document is learned **by reading** (passive). For learning **by doing** (active = reproducing a real game one mechanic at a time yourself and matching the numbers against the real ROM), see its counterpart `build-to-learn.md`.

> **How an entry is made (the 3-layer case study)**: study a commercial game through "manual (spec) × disassembly (impl) × Claude reconstruction (rehearsal)" and promote **the difference between the reconstruction and the implementation = the capability gap** into generalized prose ([[project-casebook-3layer]]). **Clean room, strictly = never transcribe disassembly code; generalized prose and the source only.** The raw pairing lives outside the repo, under `_casestudies/` inside `reference/disassemblies/<game>/`.
>
> **A Layer-1 spec is not complete from the manual alone = always add real play (observation of the real ROM)**: a manual records the "intent" of objective, controls and scoring, but conveys nothing about the screen's actual movement, quantity, drawing craft or feel. Observe the behaviour with `load_rom`→`step_frame`→`get_screen_annotated` and add it to the spec (in Fishing Derby, "one fish per row", the diagonal fishing line and the water shimmer were ALL discovered by running it = holes in the manual). [[feedback-verification-standard]].
>
> **The manual also says what to look for in the code.** Manuel Polik, 2001: *"Reading the manual of a game is also a very important thing, giving you lots of hints like 'Game Over on 99 points' 'Switch A does this'n'that'. Try looking for BCD accessed variables -> Voilà: the score!"* 〔`200110/msg00174`〕 A stated limit such as 99 points names a value to find, and a byte worked on in decimal mode is a score candidate (our reading). **Cited only, not verified.**
>
> **For Layer 2 (impl), measure it yourself BEFORE reading the disassembly** (v1.107.0): freeze a position with `save_state` and run **`probe_ram_semantics`**, and you get an exhaustive answer to "if I rewrite $XX, what on screen moves and how" (non-destructive; a full sweep of the real Combat ROM takes 3.1 seconds → 31/128 detected). The resulting classification can then be **scored** against the umbrella's `reference/ale-ram-maps/` (an external table for 104 commercial titles, ALE-derived). The order is the crux: **measure first and cross-check afterwards**, and the disassembly and that external table stay mere answer-checking without breaking the clean room. Read them first and your own observation is contaminated. Caution: a variable recomputed every frame (Combat's `XOFFS`) comes back as `none` — what the probe measures is not intent but **observable effect**.

## Breakout (Atari 1978) — the build-to-learn worked example (techniques we could WRITE)
Following the procedure in `build-to-learn.md`, working from the manual + the disassembly + a dimensional spec measured off the real ROM, **8 rungs (rung1-8) were implemented from scratch into a complete, playable one-player Breakout**. Every rung was matched numerically against the real ROM. = the demonstration that "can explain" turned into "can write it myself". Source = `reference/disassemblies/_casestudies/breakout/` (impl-map / fixtures / method-diff / layout-compare) + `roms/breakout/` (the self-built ROM, with a snapshot of each rung under steps/).

- **Situation: several vertical regions on one screen (score band / brick band / play area)** → **a multi-region kernel that switches the roles of COLUBK/PF per region** (walls = the PF edge or COLUBK; bricks = PF + a per-row COLUPF).
- **Situation: a destructible brick wall** → **hold the PF values in RAM (`brkPF0/1/2`), reload them every scanline to draw, and clear the bit that was hit = destruction** (a reflected PF simplifies this to mirrored destruction; an asymmetric PF is the better option).
  **From the forums, on finding the bit under an object (none of it run here).** Glenn Saunders, 2004, wanting the RAM strip, row and bit to turn on under a sprite for *Death Derby*, sketched a split at X > 79 (the right half re-based by −80+16, unexplained) and two linear searches through boundary tables, up to 11 iterations on rows and 8 on cells 〔`200401/msg00160`〕; Thomas Jentzsch suggested a binary search, or saving the collision registers after each row *"if there is enough free CPU time"* 〔`msg00162`〕. Dennis Debro answered from his *Climber 5*: subtract 32 colour clocks at a time to find which of the four PF1/PF2/PF2/PF1 sections of a reflected playfield the object is in, take the bit from an eight-entry `$80…$01` mask table, and EOR the index with 7 in sections 1 and 3 〔`msg00161`〕. Those flips fall where the left-half order machine-locked by `TestEveryPlayfieldColumnLandsWhereTheTableSays` (PF1 MSB-first, PF2 LSB-first) puts them, the right half taken as its mirror (our reading; the reflected half is not checked here). Manuel Rotschkar (who posted as Manuel Polik in 2001), 2004, first gave the complementary 8-entry table — one-bit-clear masks from `%01111111` — with the index EORed by 7 on the right side 〔`200403/msg00294`〕, then unrolled the flip: with PF1 and PF2 only, *"you have "r u" repeating twice!"*, so one 16-byte AND table — the eight one-bit-clear masks, then the same eight reversed — serves every position, indexed by x/4 − 4 and `AND #$0F`, with no branch 〔`msg00317`〕; he called his ideas *"all untested brainstorms"* 〔`msg00318`〕. As posted, the table opens with the D0 mask, which under the measured order belongs to column 12 (PF2's D0), not to column 4 (PF1's D7), where the code's *"skip PF0"* puts index 0: eight entries out unless x runs 32 clocks off the screen's column grid (our arithmetic). The table yields the mask only; which byte to clear still comes from x. **A third way keeps most of the board out of RAM.** Manuel Rotschkar's *Jumpman* port held a mirrored level in ROM (*"a mirrored level PF layout fits in a page at 249 bytes"*), and for the parts of a level that change used *"Timed overwrites of PF0/1 where required. The whole screen is devided in 5 separate kernels, with the two variable sections being specialized to this"*, at *"28 bytes of RAM for this level"* 〔`200409/msg00250`, `msg00257`, `msg00259`〕; two days later the most any of his seven converted levels needed was *"41 Bytes for Great Puzzle I"* 〔`200409/msg00273`〕. **Cited only, not verified.**
- **Situation: place a 1px ball and a wide paddle at arbitrary X** → **÷15 coarse (RESxx) + HMxx fine, positioning several objects simultaneously in one HMOVE**. Rendered position = RAM value − offset (calibrated by measuring with read_row).
- **Situation: controls (keys)** → paddle ± from SWCHA, serve from INPT4.
- **Situation: collision** → position-based this time (the substitution to `CXBLPF` hardware collision is recorded in method-diff for study).
- **Situation: game progression** → a small state machine of `ballLive` (awaiting serve / in play), `lives` (5 balls) and `gameOver`.
- **★The discipline of craft calibration**: both colour and dimensions **converge numerically on the original via read_row / get_screen_annotated** (judged by eye alone, the paddle was misread as "white 24px"; measured, it is "red 16px"). [[build-to-learn]] · `layout-compare.ja.md`.

## Selection criteria for the next game (scale-up)
Add keystones in **ascending order** of integration difficulty. Selection keys:
1. **ROM size / bankswitching (primary, machine-decidable)**: 2K → 4K → bankswitched (8K+). dissect annotation is also cleanest on 2K/4K.
2. **Archetype**: single screen → maze / sport / fixed shooter → scrolling / multi-screen → platformer / 3D.
3. **How detailed the manual is (the density of the spec — user's point, 2026-06-15)**: the thicker the explanation, the denser the Layer-1 spec and the richer the diff = the more that is learned. Example = **Asteroids' documentation is very thick** (but it is 8K bankswitched = the bankswitching keystone band). Manual density is a good selection signal, but reconcile it with the ascending difficulty order (1).
4. **Availability of a disassembly** (fully annotated and byte-identical to the real ROM is preferred).
5. **Same house, same period**: routines repeat within a publisher and a year, so the second game read from a cluster costs less than the first. Thomas Jentzsch, 2001: *"The Activision games I did, were all from the same period, so some of the routines are (nearly) identical, i.e. the screensaver code or the 48 pixel routines. That helps a lot."* *Surround* was *"quite hard and frustrating, because the coding was sometimes very obscure (everything ws quite new then)"*, so he meant to stay with games around 1982 〔`200110/msg00173`〕. Dennis Debro says the same of one designer: Steve Cartwright *"uses the same sort of structure for his code"*, *Seaquest* resembling *Megamania* and *Plaque Attack* (AtariAge `topic/278891`). **Cited only, not verified** — no two of these ROMs have been compared here.
6. **The author, more than the year.** Asked whether the old games were poorly written and spaghetti-like, Thomas Jentzsch, 2001: *"I think, it mainly depends on the experience and talent of the programmer."* Alan Miller, in *Surround*, the only early code he had looked at, *"was still learning"*; Carol Shaw *"was coding sometimes a bit strange, but as far as I can tell, very efficient"*; *"David Crane's coding was mostly very efficient and easy to understand"*; the *Solaris* code, which he knew *"a little bit"*, is *"very hard to understand for me, and there are very cryptic labelnames used"*, *"But the result is a masterpiece."* And: *"Spaghetti coding is often necessary on the 2600, so I wouldn't count that as a criteria if it is done for good reason."* He doubted his own fairness — *"I don't know how much time they had for completing their work"* 〔`200109/msg00318`〕. Opinions, not measurements. **Cited only, not verified.**
- **Mandatory step**: for every game, **the Layer-1 spec stands on two legs = manual + observation of the real ROM** ([[feedback-verification-standard]]). The manual alone never captures the whole behaviour.

## Reading a disassembly — ways a listing misleads
- **A read through a write-only name is a labelling error, not a feature.** SeaGtGruff: *"Since BIT is a type of read instruction (loads from memory rather than stores to memory), and GRP0 is a write-only address, I'd say any code that contains "BIT GRP0" was either "poorly" written using the "wrong" label for the intended address, or it was disassembled "wrong" using a write-only address where it should have used a read-only address."* SpiceWare in the same thread: reading GRP0 is the same as reading INPT3. SeaGtGruff's second case, from memory (*"IIRC"*): a game loading `TIM1T` (`$294`), which reads the same as `INTIM` (`$284`) through the RIOT's mirroring — *"Mirroring, coupled with read-only and write-only addresses, can complicate disassembly a bit"* (AtariAge `topic/215833`). Rename a read from a write-only register by the read map before reasoning about it. **Cited only, not verified.**
- **A disassembly can show code that cannot be moved.** Nukey Shay, posting a rough disassembly of *Rubik's Cube 3-D* in 2016: the routines reached by indirect jump take their low byte from a table, but *"this program expects that the MSB's of each address matches what is "hard-coded" there (the MSB's are not stored in a table like the LSB's)"*, so relocating one means altering the comparison value before the jump or adding an MSB table (AtariAge `topic/251486`). One ROM's case; before editing any listing, look for address halves held as literals. **Cited only, not verified.**
- **Odd code may be a fossil of an earlier version.** Manuel Polik, 2001, working through David Crane's *Outlaw*, found a constant stored to a temporary byte and then EORed from it where an immediate EOR would do, and asked whether Crane was *"just filling up the ROM with useless instructions"*. Erik Mooney's *"offhand guess"*: *"the EOR used to be a BIT instruction but was later changed to EOR. You can't BIT an immediate number; it has to be a memory location"*, left long because Crane *"didn't want to deal with having the other code move around -- perhaps had some hardcoded addresses, or just didn't want to deal with having the page boundaries move"* 〔`200109/msg00161`, `msg00162`〕. Thomas Jentzsch's guess: *"Maybe there was a label inside the code (i.E. before STY tempVar) which was removed later."* 〔`msg00192`〕 Two guesses, neither checked; before copying or "fixing" an odd idiom, list the reasons it might have been written that way (Combat's vestigial `STA WSYNC`, below, is the same kind of find). **Cited only, not verified.**
- **A disassembly shows what the code does, not what it was designed as.** Aycock and Copplestone's archaeology paper on US Games' *Entombed* reconstructed a 32-byte table from the disassembly, left one entry (input `01101`) unexplained and concluded it was hand-chosen; a follow-up drawing on the author Paul Allen Newell's development documents found the table to be an intermediate form left in the code, not the design (AtariAge `topic/296383`, read through our distillation note only; `techniques/maze.md` builds the generator). **Cited only, not verified.**
- **A shipped ROM can carry code the game never runs.** In *Adventure*, Dennis Debro pointed at an alternate start at `$F003`, five bytes that set interrupt-disable, clear decimal mode and jump to what the labelled source calls `MainGameLoop`; Thomas Jentzsch: *"I don't think there is a jump to this address inside the program. SEI and CLD indicate, that this was used as a debugging start address (without initializing anything)."* Reclaiming the five bytes is fine, he added, if *"\*all\* labels and pointers"* are converted 〔`200206/msg00012`, `msg00014`, `msg00016`〕. In *Berzerk*, by Nukey Shay's account, the ball's collision check was already in the original code when supercat's hack moved the exit blocking onto the ball, so the original programmer may have had it in mind when writing the kernel (AtariAge `topic/132083`, read through our distillation note only). Unreached or unused code can be evidence of what was planned, not only cruft to discard (the Combat lesson below is the other side). **Cited only, not verified.**

## Fishing Derby (Activision, 1980, David Crane)
Source = the manual `reference/disassemblies/_casestudies/fishing-derby/manual/` (the archive.org originals) + Dennis Debro's fully annotated disassembly (byte-identical to the real ROM). Verification = running `build/fishing_derby.bin` under Gopher2600 (2026-06-15).

- **Situation: you want a single irregular creature larger than 8px (a shark bigger than the fish, say)**
  → **shape ONE player by "stretching" it with a per-scanline NUSIZ (size / copies) + HMOVE table**. GRP stays small while the shape becomes an irregular ~40 colour clocks wide. Accept a single colour. **Neither flicker nor an extra object is needed.** Confirmed on a live run. → the principle in `design-principles.md`, "a single irregular shape wider than 8px".

- **Situation: you need a thin moving diagonal line joining two points (fishing line / tether / rope / laser)**
  → **draw a missile/ball vertically, hold the slope as integer + fraction, `adc` it every scanline, and on carry apply a ±1px HMOVE through `HMMx`/`HMBL`** (Bresenham implemented in HMOVE). Right line = BL, left line = M1. Slope confirmed on a live run. → the principle "a 1px line at an arbitrary slope".

- **Situation: you want many targets of the same kind on one screen ("6 rows of fish")**
  → **the standard answer is "one object per row × band reuse"**. All six fish are drawn one at a time by reusing P0 across 7 bands, and **the object you interact with (the hooked fish being reeled in) gets P1 exclusively**. Do not over-estimate the simultaneous object count from a noun in the manual ("rows of fish") = **first compute "how many can actually be placed given the TIA's 6 slots × band reuse"**, and only then fit the gameplay to it. 〔Claude's reconstruction wrongly assumed "the school = P0×3 + P1×3" → refuted by a live run〕

- **Situation: two facing 2-digit scores, left and right**
  → **two player slots (P0 = tens / P1 = units) + a digit font table + a re-strobe inside one scanline (redrawing GRP with a `Waste18Cycles` in between)**. A PF score suits a single or left-right-symmetric score; two facing scores want the player method. Corresponds to the existing technique `docs/techniques/score-kernel.md`. A live run confirmed "no font in the PF on the score rows = the digits are players".

- **Situation: contact between two objects of the same kind (a hazard steals the target)**
  → **one `CXPPMM` (P0 × P1)**. Don't retreat into coordinate arithmetic. Detect shark (P0) × hooked fish (P1) contact and remove the fish.

- **Situation: a cheap "shimmer" texture in the background (water / sandstorm / stars)**
  → **just stream bits of the LFSR/randomSeed you already run into `COLUBK` per band** (no dedicated RAM, almost zero cost). → the principle in the colour section, "background shimmer".

### The capability gap this case quantified (→ `capability-gap-audit.md` / `sandbox/EVALUATION.md`)
Claude's sealed reconstruction vs the implementation = **the "logic" of collision, input and difficulty is readable, but on the drawing craft that wrings the TIA dry (shaping one sprite, diagonal lines, multiple reuse, zero-cost effects) we fall short of a real veteran**. Detailed ledger = `reference/disassemblies/_casestudies/fishing-derby/diff-gaps.ja.md`.

## PONG (in-house capstone, 2026) — 4 paradigms of opponent AI and how to measure "strength"
Not a commercial-game disassembly but **a gameplay case measured and backed on our own capstone (one image → a finished PONG)** — like Breakout, an entry on the "we could write it" side. The 4 variants replace **only the AI code** relative to the mainline (physics / english / serve / sound / score are completely identical = a pure comparison), and every one of them passed the hardware budget check (all physics lines ≤ 76cy, 900f over:false). Source = `sandbox/practice/pong/ai-variants/` (README = the design of the 4 variants; `bench/README.md` = the objective bench + the measured round-robin, 2026-07).

- **Situation: you need a beatable opponent AI (paddle games)**
  → choose from the **4 major paradigms** of classic PONG AI. The key = **the way to beat it is a design INPUT, not an afterthought** (leave every type a structural way to lose):
  | Type | Mechanism | The way to beat it (designed beatability) |
  |---|---|---|
  | tracker | follows the ball's current Y with a lag (re-samples once every 8 frames, 3px) | beat the one-beat re-sampling lag with a fast ball or an angle change |
  | predictive | a shadow ball (advances at twice the real ball's speed, **wall reflections included**) fixes the arrival Y → it waits there in advance | an angle change after the arrival is already fixed (english / the WHAMMY fast ball); the injected misread (reads it backwards 1 time in 16) |
  | anticipatory (lookahead) | linear extrapolation, target = BallRow + 4×BallDY, a continuous 2px every frame (smooth) | **it does not read the walls** = it leads a bouncing ball to the wrong place |
  | rubberband | modulates the **error width** by the score difference (losing = tighten / winning = sloppy), speed fixed at 2px | it slackens once it leads, plus the human's instantaneous speed advantage (WHAMMY ±3 > the AI's 2px) |
- **Situation: you want to tune the AI's "character" = its imperfection**
  → build it out of **error and latency**, not speed: inject an aiming error AIErr (move its generation onto a line with slack), a reaction delay (the re-sampling interval), and a speed cap. Variable difficulty means "**modulating the error width**" (modulating speed is visible to the eye, modulating error is hard to spot = the standard move in game AI).
- **Situation: the kernel budget is too tight to raise accuracy**
  → **free up budget by skipping a shared tail that an exclusive path does not need**: in v2 the paddle does not move during the prediction phase = the shared tail's PaddleR_End recomputation (10cy) is unnecessary → `jmp OverEnt` goes straight to the housekeeping line. **The 10cy freed upgraded the shadow ball's slope from approximate (X speed fixed at 3) to exact (2×BallDX = exact at every speed).** A variant of design-principles' "lodging on a physics line" = find the shared work a particular path does not need, drop it, and spend what is freed on accuracy.
- **Situation: you want to measure how strong an AI is (evaluation, balancing)**
  → **a single-baseline bench is only one lens, and it can get the ranking exactly backwards (measured)**. First-to-11 against a fixed baseline AI (a deterministic 1px tracker) gives v4 11-0 / v1 11-1 / v3 1-11 / v2 1-11 = "v4 > v1 > v3 ≈ v2". But **the truth from the round-robin (head-to-head, porting each AI onto the left paddle and mirroring left/right to remove side bias) is v3 ≈ v4 > v2 > v1** —— v1 is the weakest at 0 wins 3 losses (a real AI exploits its 8-frame re-sampling lag), and v3/v4 stay a perfect 0-0 deadlock even over 37000 frames. Mix the baseline back in and you get a **cycle, v1 → baseline → {v2,v3} → v1 = strength is non-transitive (rock-paper-scissors)**. Furthermore **an objective bench ≠ difficulty against a human**: v3 scores 1-11 against the perfect-tracking baseline and reads "weak", but against a human whose tracking is imperfect it reads "medium — you can just about win", which is why it was adopted for the mainline. Lesson = **AI strength depends on the opponent and is not one-dimensional. Real evaluation means a round-robin plus a variety of opponent models** (→ the gameplay-verification frontier in the harness backlog).

## Combat (Atari, 1977, Larry Wagner) — dual score with zero player slots, multi-frame bounce solving, a bit-packed 27-variant shell
Source = the disassembly `reference/disassemblies/.../Combat.asm` (Larry Wagner original / Roger Williams 2002 annotation), read as the casebook "disassembly-reading" layer; distilled in `sandbox/studies/combat/comparison-structure-vs-original.ja.md` + `diff-gaps.ja.md`. Clean-room: generalized prose + routine names only, no code transcribed. Cross-checked against the self-built `combat_mine`.

- **Situation: two independent 2-digit scores, but BOTH players (P0/P1) are permanently occupied by the moving tanks**
  → **draw both scores from the PLAYFIELD, never from a player.** Combat sets `CTRLPF #$02` (SCORE mode, NOT reflect) so the left half takes `COLUP0` and the right half `COLUP1` = two independently-colored scores out of one repeated field, carried by a SINGLE `PF1` register **recycled** across the kernel (the previous line's `NUMG` is computed while `PF1` is reused), `PF1` write pinned to cycle 9. Digit glyph offset = `SCROT` turns each BCD nibble into a ×5 index with `ASL`/`ASL`/`ADC` (clean NMOS BCD nibble), 5-line font. **The object-slot decision follows "what permanently owns the screen": tanks own P0/P1 → score goes to PF; PONG's thin paddles let P0/P1 double as score (`docs/techniques/score-kernel.md`).** Contrast: Combat = SCORE-mode per-half coloring + one recycled PF1; `docs/techniques/asymmetric-pf-score.md` = repeat-mode, PF1+PF2 twice/line for 4 fields. 〔`SCROT`/`NUMG0/1`/`CTRLPF #$02`/`NUMBERS`; diff-gaps GAP-2, comparison §2.5〕
- **Situation: a bullet must reflect off a maze wall, but the TIA collision latch reports only "hit playfield" — never WHICH wall face**
  → **reconstruct the wall normal over multiple frames with a trial-and-error state machine (`MxPFcount`), zero geometry math.** frame0 try vertical reflect → frame1 (still inside) flip 180° = horizontal → frame2 wait (grace to clear) → frame3+ corner reflect, held until the bullet escapes; each frame re-observes "still in the wall?" and picks the next hypothesis — the missing hardware fact (which face) is recovered by hypothesis-testing across time. `COLcount` ignores contacts under ~4 frames (a resting tank isn't shoved). **Lesson: when the hardware under-reports, replace the one-shot formula with an observe-then-choose state machine that spends frames to disambiguate.** 〔`MxPFcount`/`COLcount`/`BounceCount`/`CXM0FB`; diff-gaps GAP-4, comparison §2.6〕
- **Situation: the "got hit" reaction needs game-feel, not just a blink**
  → **a dedicated `StirTimer` state machine seizes the loser's tank**: spin it like a top with `INC DIRECTN` every frame, decaying explosion via `BoomSnd` (AUDV/AUDC/AUDF ramp-down), knockback via `RushTank`; the winner's engine sound is silenced. Score-on-hit seeds `StirTimer` with the loser's ID. **The hit reaction is its own mode that suppresses input — even a 1977 title invests in feel; don't model "hit" as a mere flash + respawn.** 〔`StirTimer`/`DIRECTN`/`BoomSnd`/`RushTank`; diff-gaps GAP-6, comparison §2.6〕
- **Situation: one 2K ROM must be 27 game variations toggled by the console switches**
  → **one bit-packed descriptor byte per variation → fast flag bytes; freeze joysticks in software while no game is on.** `GSGRCK` reads `SWCHB` (RESET=new game; SELECT+debounce=advance, wrapping to game 1); `VARMAP` holds one packed byte per game, fanned out into 4 flag bytes (`$82-$85`: PF_PONG/GUIDED/BILLIARD/GAMSHP) tested with cheap `BIT`; `ClearMem` reuses ONE wrap loop for 4 erase ranges by re-seeding X. The joystick freeze is **software, not the port DDR** (corrected 2026-09-28): before the stick is decoded the code reads `GameOn` (a RAM byte, written with `STA zp`) and, when no game is on, loads `$FF` so no direction registers — bytes `24 88` (BIT) / `30 02` (BMI) / `A9 FF` (LDA #$FF) at $F316 of the ROM. The joysticks are on port A (`SWCHA`), which a port-B DDR could not gate anyway; what the ROM does write is `SWBCNT = #$10` once at start-up ($F00A) and `GameOn` into the port-B *data* register `SWCHB` ($F58F). **Steal when adding variants: one bit-packed descriptor per config → fast BIT flags, plus one flag test to freeze input.** 〔`GSGRCK`/`VARMAP`/`GAMVAR`/`ClearMem`/`GameOn`; freeze bytes read from the ROM, `sandbox/studies/combat/Combat.bin`, not from the labels; diff-gaps GAP-E, comparison §2.8〕
- **Situation: a control lookup table is indexed by the RAW joystick nibble, and one input combination is "physically impossible"** — an ANTI-PATTERN, not a technique to copy
  → **do NOT leave that slot as an undefined-behavior sentinel: a table indexed by external input must be dense-and-defined for EVERY bit combination, or the index must be masked/clamped BEFORE the lookup.** Combat's `CTRLTBL` (12×3, 4-wide rows) parks `$FF` in the 4th slot of each group — the up+down-simultaneously index a healthy stick can't assert — and builds the index from the raw low nibble with NO clamp. A shorted/modded controller or a stuck switch that asserts up+down together fetches `$FF`, read as rotation=$F (full CCW) AND velocity=$F (warp speed); the annotator warns that "indexing out of bounds with impossible joystick movements will cause strange behavior." The only "safety" is the assumption that the hardware can't produce the input. **Lesson: undefined-behavior-by-omission. Never lean on "that input can't happen" — sanitize the index (mask/clamp) or define every slot; a master shipped exactly this bug.** 〔`CTRLTBL`/`CtrlBase`; deep-read harvest 2026-07-23〕
- **Situation: you are studying or porting a hand-tuned commercial master and tempted to treat every line as load-bearing**
  → **don't cargo-cult even a 2K master — a shipped ROM carries dead cruft, luck-dependent seeds, and deliberately uninitialized state; verify each construct actually earns its keep before reusing it.** Three annotator-flagged imperfections in Combat: (a) `InitPF` runs a vestigial `STA WSYNC` the annotator calls out as "there is NO reason!" — a wasted line likely left from an earlier kernel-timed version; don't preserve a stray beam-sync as if it gated timing. (b) `START` seeds `GameOn` to an invalid `$10` by REUSING the just-loaded Port-B DDR constant, though its only valid states are `$00` (attract) / `$FF` (playing); it survives purely by luck because $10 has none of the bits any path tests before the first real write — don't seed a two-state flag with a third value "because A already holds something." (c) `MPace` sits ABOVE `ClearMem`'s `$A2` ceiling and is NEVER zeroed at power-on, safe ONLY because every consumer reads it modulo (parity/low bits over time) so the absolute value is irrelevant — a single future absolute compare would read garbage. **Lesson: a master's imperfections survive shipping precisely because nothing observes them — reuse the technique, not the cruft.** 〔`InitPF` STA WSYNC / `START` `GameOn`=$10 / `MPace` vs `ClearMem` $A2 ceiling; deep-read harvest 2026-07-23〕
  **Teaching material and released source carry the same risk.** crackers, 1997, to a newcomer working from his playfield bat demo: *"Did you fix the bug in the verticle blanking subroutine? Without the fix the programme won't work on a real 2600 (it'll work on the emulators though)"* 〔`199703/msg00264`〕; two days later, a second fix, this time to the demo's annotations — `LDY * LDX = 192` *"should read LDY * (LDX+1) = 192"* 〔`199703/msg00280`〕. Neither message says what the bug was. batari, 2005, explaining why none of his source was out yet, pasted a run of commented-out lines from one of his games and left it at *"I think you get the picture"* (AtariAge `topic/71987`, read through our distillation note only). Dennis Debro on *Seaquest*: *"There are 10 RAM bytes not used. I wonder if they were for a feature that got removed before release"*, and ROM tables nothing references (AtariAge `topic/278891`). Eckhard Stolberg, 1999, on the three `STA WSYNC`s at the top of Nick Bensema's *How to Draw a Playfield*: one makes VSYNC start at the start of a line, *"The other two: well I suspect that Atari's programmers first used screen loops with register counters for 256 scanlines"*, the routine later pasted into real games and copied from one of them; *"They are actually unnessesary"* 〔`199909/msg00050`〕. In 2000 John K. Harvey, to Rob, another poster — *"you were getting 265, right?  That'd be 3 extra"* — recalled that thread 〔`200001/msg00026`〕; the reply does not say what the cause had been 〔`msg00027`〕. **Cited only, not verified.**

## From the forums — testimony, not disassemblies
These entries rest on what authors said, not on a ROM read here. Each is **Cited only, not verified**.

- **Situation: each seat may be a human or the computer**
  → **one indirect-jump vector per player, filled at game start; each turn is just `JMP (PlayerNTypeVector)`, with no decision logic in the turn.** Christopher Tumber, 2003, answering a beginner's book that called indirect JMP useless: *"For each player, you setup an indirect JMP vector. If it's a computer player, the JMP vector points to the subroutine to make a computer move. If it's a person, you set the JMP vector to point to the routine to input a move from the player. For each player's "turn" you just have to JMP (Player1TypeVector) JMP (Player2TypeVector) etc and there's not decision making logic involved."* 〔`200305/msg00012`〕 The cost is two bytes of RAM per vector, which must be written before the first turn (an unwritten vector jumps wherever power-on left it — our addition); and a vector must not start at `$xxFF`, where the 6502 takes the high byte from `$xx00` — the same message describes it, and `litmus_6502` measures it. What sits behind the computer's routine is the PONG entry above. The dispatch has not been built here.
- **Situation: porting a game from another 6502 machine**
  → **expect a rewrite.** Andrew Davie: *"I "ported" my own game, Qb (1984) from the Atari 800 to the Atari 2600 in about 2003. It was a complete rewrite. Very little shared, zero code re-use."* azure, in the same thread, drew the line: simple utility subroutines may carry over, *"but if they rely on large data structures in RAM those will be a rewrite too."* Mr SQL suggested early 400/800 games that did not use ANTIC might port with more reuse, naming one, *Basketball* (AtariAge `topic/302929`, 2020). The author's own account, not a measured diff.
- **Situation: more things move than the five objects can carry**
  → **read the allocation off games that shipped one.** `design-principles.md` gives the order (colour budget → assignment table); these are filled-in tables, as players described them.
  - *Super Breakout*: *"the side walls of Super Breakout are drawn - player1 on one side, missile1 at 8 pixels wide on the other, ball for the ball, player0 for the paddles, flicker missile0 for the second and third balls if necessary"* (Erik Mooney, 1998, 〔`199801/msg00298`〕).
  - *Road Runner*: Eckhard Stolberg, 1997, *"I think"* — Road Runner player 0, Wile E. Coyote player 1, the bird food and bombs missile 0, the truck's left half the ball and its right half missile 1, read from colour: the right half *"changes it's colour, when Coyote is on screen"*, and *"The left half of the truck first has the same colour as the road marks, which are playfield graphics, until it has been drawn over them"* 〔`199705/msg00057`〕. Kurt Woloch, 1999, also put the cars on missiles and/or balls, *"because the two players are already assigned to Road Runner and Wile E. Coyote"* 〔`199905/msg00034`〕.
  - *Space Invaders*, *Missile Command*, *Asteroids* (Erik Mooney, 2000): the invaders are players, rows shifted *"just to hit RESP0 and RESP1 at different times"*; and in the two-missiles-each mode reached by holding RESET at power-on, *"all the missiles are actually the ball"*, yours and theirs on alternate frames. Missile Command's incoming missiles are one player, cloned; *"The missiles you launch and their explosions are all drawn by the other player, flickering horribly - it alternates between _three_ different sprites with one hardware object. The cursor is the ball."* Asteroids: he first wrote that the up-moving and down-moving rocks take alternate frames, then after looking again, *"All the asteroids - both sequences - are drawn on the same frame. Then on the next frame, the player, his bullets, and the enemy saucer and bullets are drawn"* 〔`200005/msg00154`, `msg00162`〕. His 1997 account of Missile Command, in the next entry, gives the cursor to player 0 and the explosions to the ball and missiles; the two are not reconciled here.
  - *Super Challenge Football*: the ball takes the playfield's colour, so the two swap — over dark green the background is dark and the playfield/ball light, but on a light yard stripe *"the playfield is actually the dark green and the background is light green, so that the dark green ball can show up over the light green background"* (Erik Mooney, 1999, 〔`199905/msg00028`〕).
  - *Stay Frosty 2* (SpiceWare's development blog, AtariAge blog `entry/11619`, read through our distillation note only): the snowball went to missile 0 because the ball, in the playfield colour, vanished over ice blocks; the ball could not be a free-moving platform for lack of cycles and became one elevator per zone; the score/lives display was rewritten with a mid-line NUSIZ change to stop it flickering, which was incompatible with a missile-drawn carrot nose, so the nose is drawn with the playfield.

  **Cited only, not verified.**
- **Situation: you want to know how a game's kernel works and have only the picture**
  → **read it off the screen; spacing, offsets and limits are evidence about cycles and objects.** Eric Fischer, 1998, putting in *Slot Machine*: three 16-pixel-wide shapes per line, *"not tightly spaced like the standard 6-sprite approach. All the shapes seem to be bilaterally symmetric, so I'm guessing both players are set to wide spacing and the same data is being put into both of them, and the intervening 16 pixel space gives enough time to do an indexed load. It looks like there's something going on with the vertical delay registers, too, because the right two digits of each player's score are offset by a scanline from the left two digits."* 〔`199805/msg00100`〕 Erik Mooney, 1997, from the black "comb" on the left: *"If I'm right here, Missile Command repositions ... one sprite every other scanline (hence the "comb" on the left)"*, the missile groups drawn with player 1 on alternate frames, *"leaving player 0 to draw the cursor"*, and *"It also appears to use the ball and missile graphics to display the explosions, hence the limit of three explosions simultaneously"* 〔`199703/msg00215`〕. Guesses, in their authors' words; on a running ROM the same questions have numeric answers from `read_row` and `beamtrace`. **Cited only, not verified.**
- **Situation: a document states a hardware constant, and a shipped game seems to correct for a different one**
  → **read what the game corrects for.** Bradford Mott, 1998, while writing Stella: *Atlantis* strobes RESP0 for the leftmost gun right after a WSYNC, during horizontal blank, and later moves it with HMP0 = `$30`, three pixels left — *"This seems to imply that it really positions it at pixel 3 and not pixel 0 like the Stella Programming Guide says"*; a trace from his emulator showed the sequence 〔`199804/msg00176`, `msg00192`〕. John Saeger: *"I think the gun is \*really\* at position zero"*, the HMOVE *"spurious; a bug that turns out not to matter"*, and *"so far, I'm a firm believer in the RESP during HBLANK putting the object at zero theory"* 〔`msg00181`〕; Eckhard Stolberg's arithmetic put it at pixel 1 after the move 〔`msg00190`〕. Here the floor is measured: a normal-width player strobed at cycle 21 or earlier stops at x = 3, on a line with no HMOVE (`techniques/sprite-placement.md`, rule 7) — Mott's reading. That the HMOVE then carries it to 0 is arithmetic, not measured. A correction in a shipped game is evidence about the hardware its authors saw, though as Saeger's reply shows it can be read as a fudge. **Cited only, not verified** for *Atlantis*.
- **Situation: the screen jumps while a level is set up, and a title screen is wanted too**
  → **fix the jump first, with whatever space can be freed.** Eckhard Stolberg, 2001, to Andrew Davie on *Qb*'s first alpha: *"one thing that isn't really a problem, but more a case of making your game look 'professional': When a new level starts, the setup routines take so long that the screen jumps. Before you go and add a title screen to the game, you might want to use the space that you can free up to fix this problem. I think this would benefit the appearance of the game more."* 〔`200102/msg00352`〕 The fixes are in `techniques/blank-a-frame.md`, which quotes the same writer on the same symptom in *Thrust* and *Jammed*. One reviewer's order of work, not a rule. **Cited only, not verified.**
